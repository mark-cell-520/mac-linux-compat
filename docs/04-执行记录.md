## 第二轮：自研翻译层（v1，成功）

### 2.1 架构定型

- 加载：ET_DYN 镜像由内核选基址整段映射，段内容拷贝，按段 mprotect（本机 macOS 27 禁 RWX 映射，且 mprotect 是 16K 页粒度）。
- 拦截：可执行段内 svc #0 → BL 蹦床（蹦床紧随客户机映射，保证 BL ±128MB 范围内）。
- 蹦床：clang 汇编产出 33 条指令（src/stub.s），四条 movz/movk 立即数运行时修补为 C 处理器地址；关键修正——blr 会覆写 LR，存根必须保存恢复 x30。

## 第四轮：v1.1 客户机地址空间约束（2026-11-06）

目标：清掉审计的三个中等问题（M1 指针校验、M2 目录句柄泄漏、M3 munmap 精度）

   野指针用例实测 SIGSEGV 崩溃退出码 99，确认为真红。

第五轮修出的缺陷（全部实测复现过）：
F14. svc→BL 覆写 LR，glibc leaf 形 inline syscall 包装直接死循环。
     ld.so 卡在 __munmap 返回点，PC==LR，看门狗抓到偏移 0x1B5CC，全程只有 13 次系统调用。
     修法：svc 改修补成 B（不写 LR），每个 svc 配一份独立蹦桌副本，
     副本末尾用可运行时修补的 B 立即数编码「该 svc 的下一条」返回客户机。
F15. brk 起点取「主镜像末段之后」，而镜像映射实际跨度是 span+0x14000（含间隔与蹦桌），
     客户机 brk 增长用 MAP_FIXED 直接覆盖蹦桌。修法：brk 改独立 32MB 预留区。
F16. mmap 取整下溢：addr==0 时 map_addr=0x100000000 而 map_end=page_up(len)，相减成天文数字，
     所有匿名 mmap 必返回 ENOMEM（ld.so 早期全挂）。
F17. 可执行文件映射匿名化时把 MAP_FIXED 一并剥掉，macOS 把库映射到别处，
     引擎却把客户机请求的地址当成功返回，客户机随后访问未映射内存。
F18. mmap 对「文件映射 + PROT_EXEC」返回 EPERM（macOS 代码签名强制），
     且 offset+len 超文件尾直接 ENOMEM（Linux 只在那页 SIGBUS）。
     修法：所有文件映射统一走「匿名映射 + pread 读入内容」。
F19. macOS 对 MAP_FIXED 部分重叠现有映射返回 ENOMEM。修法：MAP_FIXED 前先 munmap 腾空，
     等价于 Linux 内核 elf_map 的原子替换语义。
F20. v1.1 加的 MAP_FIXED 安全约束（region_covers）把 ld.so 的 zero-fill 洞和新库段
     一律拒绝，动态链接直接失败。修法：改为「只禁止覆盖引擎保护区（镜像+蹦桌），其余地址允许」。
F21. 动态库（libc 等）由 ld.so 映射，不经 load_image，里面的 svc #0 未被拦截。
     修法：sys_mmap 对可执行映射现场扫 svc、建邻接蹦桌、运行时修补。
F22. 动态蹦桌未纳入引擎保护区，ld.so 后续 MAP_FIXED / munmap 会覆盖或卸掉它，
     之后系统调用跳进已卸载页（SIGBUS，PC 正是蹦桌地址）。修法：蹦桌纳入保护区，
     munmap 也过保护区检查。
F23. getdents64 断言改为自建子目录后，静态测试的文件也要跟着搬进 rootfs
     （客户机看到的 / 就是 rootfs，v1.2 路径重写语义）。

诊断基础设施（本轮新增，保留）：
- MLC_WATCHDOG=秒数：死循环时超时打印 PC/LR/SP/全部通用寄存器、handler 累计次数与

### 5.1 B1 客户机地址窗口架构（已实现，未跑通）

实现内容：
1. 客户机地址窗口：池 16MB + 窗口 96MB 一次映射、物理相邻。客户机 body 从窗口取，
   主程序从低端 bump-up，interp 从高端 bump-down，中间留 48MB 间隙专供 ld.so 向下分配。
   蹦桌全部进池，任一库到池距离 < 112MB，B 跳转必然可及。
2. 蹦桌与客户机映射彻底分离：曾紧邻映射，ld.so 会复用那块地址把新库 MAP_FIXED 到蹦桌上
   （或 munmap 卸掉蹦桌），之后系统调用跳进被替换/已卸载的页。
3. 引擎保护区（guard）表：镜像映射与蹦桌池都登记，MAP_FIXED / munmap / mprotect 一律不得覆盖。
4. sys_mmap 对可执行映射现场扫 svc 并建蹦桌；sys_mprotect 改成可执行时补扫
   （ld.so 会把先映射为 RW 的段改成可执行）。
5. load_image 也改为窗口取 body + 蹦桌紧随本镜像同一映射（池只留给 ld.so 动态映射的库）。

本轮新增修复（续 F 编号）：
F24. 窗口分配的地址没加 MAP_FIXED，被 macOS 当 hint 忽略，库全部映射到窗口外，
     窗口布局与 B 距离全乱。修法：引擎自选地址一律 MAP_FIXED。
F25. mprotect 把「末端绝对地址」当成长度传，长度成天文数字，所有 mprotect 都 ENOMEM，
     ld.so 报 cannot change memory protections。修法：长度 = 末端 - 起点。
F26. v1.1 的 MAP_FIXED/munmap/mprotect 白名单（region_covers）把 ld.so 的 zero-fill 洞、
     新库段、对齐 padding 一律拒绝。修法：一律改为黑名单式（只禁引擎保护区）。
     取舍记录为 D12：客户机理论上可 mprotect/munmap 宿主任意地址，但引擎地址猜不中。
F27. 蹦桌按页取整分配，副本之间留下未初始化空洞，B 落进空洞就是执行 0x00000000（SIGILL）。
     修法：蹦桌副本按 128 字节紧邻排布。
F28. 试图用「报大内存 phdr 的 filesz/memsz」把 ld.so 的分配起点推远：对 glibc 无效
     （实测目标地址毫无变化），且 mkelf 测试载荷的 phdr 与代码重叠，memcpy 直接覆盖代码
     导致 SIGILL。已移除该 hack。

剩余阻塞（下一轮首要）：
B4. ld.so 给新库选地址的基准落在主程序内部：实测目标恒为 主程序基址 + 0x3c000，
    而 0x3c000 正是主程序第二个 PT_LOAD 的宿主 16K 页起点（客户机 4K 页起点是 0x3e000）。
    宿主 16K 页让主程序 data 段多占了 [0x3c000, 0x3e000)，而 ld.so 想用的正是这块。
    报大 phdr 无效（F28），按段映射（把洞留给 ld.so）也被同一地址挡住（该页仍属 data 段），

B5. libc 加载成功后的符号解析报 "undefined symbol: _res, version GLIBC 2.17"

### 5.2 B4 突破：窗口统一选址（2026-11-06）

读 glibc 2.39 源码（elf/dl-map-segments.h、dl-load.c）确认：_dl_map_segment 对**第一个段**
用的是无 MAP_FIXED 的 hint（mappref = ELF_PREFERRED_ADDRESS(loader, maplength, mapstart)），
后续段才用 MAP_FIXED 到 l_addr + mapstart。因此引擎必须精确满足 hint，否则 ld.so 记录的
基址与实际映射脱节，后续段全落错位置。

据此修掉两个选址缺陷：
F29. PROT_NONE 匿名预留走「让内核自选」分支，libc 被映射到距主程序 143MB 之外，
     B 跳转直接越界，libc 的 svc 全部拦不住。修法：非 MAP_FIXED 的映射一律从客户机
     窗口取地址或满足 hint，不再让内核自选。
F30. hint 路径曾限定「必须在窗口内」，窗外 hint 被改分配到别处，导致 ld.so 的 l_addr
     与实际映射不符。修法：只要不与引擎保护区冲突就满足 hint。

修完后 MAP_FIXED 保护区冲突完全消失，ld.so 走到 glibc 初始化尾段：
set_tid_address、set_robust_list、rseq（返回 ENOSYS，glibc 正常降级）、
两处 RELRO mprotect 全部成功——共 43 个系统调用，无一未实现。

剩余阻塞（只剩一个）：
B6. 最后 SIGBUS：PC 在 ld.so 内偏移 0x51d0，故障地址落在客户机窗口内、主程序之后、
     ld.so 之前的那段 48MB 间隙里（该区域本应可访问，因为窗口整体是 RW 映射）。
     怀疑是客户机 munmap 卸掉了窗口内某块后，ld.so 仍持有指向该块的指针；
     或 munmap 的页取整范围比请求范围大，卸掉了相邻有用区域。
     下一步：打印 munmap 的精确范围与该块后续访问，核对是否多卸。

### 5.3 B6 突破：动态链接全通，ls/cat/echo/bash 实测通过（2026-11-06）

5.2 节把 B6 列为「只剩一个崩溃点」。实际收掉它用了六轮，每轮一个真实缺陷，
根因都不在 5.2 猜测的两个方向（munmap 多卸、持已卸指针）上，而在更下面一层。

第一步是加诊断而不是改代码：mmap 的每次决策与窗口游标、munmap 的精确范围、
崩溃时的客户机区域表/镜像表/蹦桌池/窗口游标、故障指令与所在宿主页的真实权限、
以及全部通用寄存器。有了这些才发现 5.2 的猜测方向是错的。

F31. munmap 的「页内残余 PROT_NONE」会顺手打死相邻映射。
     现象：客户机 munmap 一段 4K 边界区间，宿主按 16K 页取整，`mprotect(残余)` 的
     长度被 macOS 向上取整到整页，把同一宿主页内相邻映射的数据打成不可访问。
     修法：只卸完整的宿主页，页内残余一律不碰。代价是客户机「卸了但还在」的
     子页区间仍可访问，记入已知边界。

F32. 窗口栈式复用把活映射算成空闲（B6 的真正根因）。
     现象：`win_free_top` 把窗口低水位退到 `page_down(munmap 起点)`，而宿主页是
     16K、客户机页是 4K，退下去的那一段仍被相邻库的映射占着。下一次 win_alloc
     把新库 MAP_FIXED 上去，就把那块活数据静默替换了。实测 lib A 的 data 段
     被 libc 的预留区整段抹掉，ld.so 随后读到被抹掉的链接结构，算出野指针
     写进 libc 只读文本页，SIGBUS 收尾。
     修法：`win_free_top` 反复跳过仍然活着的区间，只退到「确实已经空了」的边界。

F33. 引擎保护区护住了客户机自己的段。
     现象：ls 走到最后一步报 cannot apply additional memory protection after
     relocation。根因是 guard 表把镜像的整个 total（含客户机内容）都登记了，
     glibc 收尾对自己的 RELRO 发 mprotect 被挡成 ENOMEM。
     修法：guard 只从 span 之后开始，客户机内容 [body_at, body_at+span) 留给它自己。

F34. macOS libSystem 会清掉客户机的 TPIDR_EL0。
     现象：`__open_nocancel` 的 `str w3, [x2, x1]`（x2 = mrs TPIDR_EL0）崩在
     NULL+0x110。实测：客户机 msr 写进去之后，只要 open() 一次，TPIDR_EL0 就读回 0。
     修法：蹦桌进 C 处理器前先 msr 清零（不让 macOS libSystem 把客户机 TCB 当成
     它自己的 pthread 结构用），返回前再写回客户机原值。

F35. AT_PAGESZ 报了 4096，宿主页其实是 16384。
     现象：ls 把目录列表写到 fd 0 而不是 fd 1，且 libc 的 .data 尾部（含
     `_IO_2_1_stdout_`）整段变成零页。根因：客户机按 4K 对齐算 mapstart/mapsize，
     引擎只能按宿主 16K 页落位，一次 4K 边界的 MAP_FIXED 被展成 16K，把同宿主页内
     仍被 .data 使用的部分连带卸掉重建成零页。
     修法：auxv 的 AT_PAGESZ 报 16384，让 glibc 的对齐与宿主页粒度一致。
     这一条同时消掉了整类「客户机页粒度 vs 宿主页粒度」问题。

F36. gettimeofday 被误认成 getpgrp（本轮自查抓到的回归）。
     现象：补 bash 作业控制缺的 169 号时按 getpgrp 实现，客户机每次取时间都拿到
     一个进程组号，属静默数据损坏。靠 trace 里实参形状（ptr, NULL, ptr）才纠正。
     教训：按系统调用号补实现时，编号必须从实参形状或权威表双向确认，
     不能靠「这个名字大概在这儿」。

修完之后实测（2026-11-06）：
- `mlc ls` / `mlc ls -la /`：完整目录列举，含权限、符号链接、时间戳
- `mlc cat /etc/hostname`：文件读入
- `mlc echo ...`：参数透传
- `mlc bash -c 'echo hi; pwd'`：bash 内建命令
- `mlc ls /nonexistent`：退出码 2 原样透传
