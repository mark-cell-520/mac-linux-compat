# 风险登记表

日期：2026-11-06（v1.6.1 更新：F60-F63 四个"门禁全绿但产品不可用"的缺陷已修并转入 docs/08）
用途：把未结缺陷按"挡住什么"分级，先修阻塞级。与 docs/10-整改清单 的分工：
docs/10 记"改了什么、怎么验的"，本表记"还有什么没结、结在哪里、有多疼"。
状态取值：未修 / 已修待回归 / 观察中。

## 登记原则

1. 定性不以单次成功率下结论。触发概率是"单次调用失败的概率"，不等于用户可见的
   失败率——用户跑一条命令可能触发几十次调用。以 20 个常用程序连跑实测为准。
2. 没有观测手段的只挂观察项，不写成缺陷也不写成正常。观测不到 ≠ 不存在。
3. 不修一个缺陷，等于不知道它是否存在。凡是靠"目前没人踩到"活着的，都登记。
4. 有置信区间的观测项，先修观测再修缺陷。看不到失败率就没法判断改动是修好了
   还是只是这次没触发。
5. 与本次改动无关的既有缺陷单独记，不挂在当前里程碑名下——挂错了会让下一个人
   去改错的地方。

## 2026-11-06 补测：M2 的真实影响面，以及"装个解释器进来"卡在哪

起因是用户要求「在 mlc 中安装 hermes agent」。为了判断可行性，先把 rootfs 的
PIE 构成实测了一遍，并真的把 Python 装了进来。三条结论都有证据。

一、M2 的影响面比登记的小得多，但卡的位置比登记的致命得多。
全 rootfs 逐文件读 ELF 头：AArch64 ELF 共 776 个，ET_DYN（PIE）775 个、
ET_EXEC（非 PIE）1 个。原先登记的「约 60 个 ELF 不含 PIE」不成立——那个数
无论指哪个快照都对不上，实测就是 1。**但偏偏这 1 个就是 Python**：Ubuntu
noble 的 /usr/bin/python3.12 是 ET_EXEC，链接在固定地址 0x400000-0xa1fd98，
入口 0x5f6240。Debian 也一样：bookworm 的 python3.11-minimal 拆开看，
/usr/bin/python3.11 同为 ET_EXEC。两个发行版都把 Python 编成非 PIE，
所以「换源」绕不过去，只有实现 M2 这一条路。

二、Python 已经装进 rootfs 了，但起不来。
按 apt 依赖闭包从 ports.ubuntu.com 下了 11 个包共 6.8MB（python3.12、
python3.12-minimal、libpython3.12-minimal、libpython3.12-stdlib、libexpat1、
libreadline8t64、libsqlite3-0、media-types、netbase、readline-common、tzdata），
以「目标已存在就跳过、绝不覆盖」的方式解进 rootfs/sysroot，新增 1285 个条目，
原有 2578 个文件一个没动。实测 `mlc python3.12 --version` 直接失败：
「无法映射客户机段（非 PIE 镜像请用基址重写引擎）」。也就是卡在 M2 上，
一步都没进去。这些文件先留着（rootfs/sysroot 本就在 .gitignore 里），
等 M2 落地就是现成的验证载荷。

三、M2 不是加个分支就行，它动的是加载器的地基。
python3.12 要落在 0x400000 一带，而客户机窗口在 0x108000000 一带、蹦桌池在
窗口旁边，两者相距约 4.3GB——远超 B 指令的 ±128MB 射程。要支持 ET_EXEC，
至少得同时解决四件事：镜像按固定地址 MAP_FIXED 落位、在镜像旁边再开一个
蹦桌池（现在池子是单例全局）、brk 预留区改到镜像数据段附近（Linux 对非 PIE
的 brk 起点就在可执行文件末尾往后）、区域表与野指针校验认下这块新范围。
这是一项独立工程，不是本轮能顺手带走的。

三补（2026-11-06 晚二轮更正）：上面四件事里的第一条「镜像按固定地址
MAP_FIXED 落位」**已被实测否决**——宿主在 4GB 以下做 MAP_FIXED 一律 ENOMEM
（证据见文末第二节）。所以 M2 只能走「重定位到客户机窗口 + 改写固有地址」，
四件事要整体重写，代价比原登记更大。

## Hermes Agent 的完整阻塞链（2026-11-06 逐条核过）

Hermes-Agent 本体在 ~/.hermes/hermes-agent，1.3GB，Python（要求 3.11-3.15，
入口 run_agent.py）+ Node workspaces + Electron 桌面端，82MB venv。
要它在 mlc 里跑起来，需要按顺序打通五道闸，每一道都是独立工程：

| 顺序 | 闸门 | 现状 | 证据 |
|---|---|---|---|
| 1 | 非 PIE 支持（M2） | 未实现 | python3.12 是 ET_EXEC，`mlc python3.12 --version` 直接失败 |
| 2 | dlopen（B4） | 未实现，但可能已半能用 | libpython3.12-stdlib 带 44 个 lib-dynload/*.so，import 时逐个 dlopen；已确认 ld.so 自己完成映射，且 mlc 在 mprotect（nr=226）上有补扫站点这条路，所以可能不用新写机制，但必须实测 |
| 3 | socket 家族 | 一个都没有 | mlc-core.c 里 63 个 case，无 socket/connect/bind/listen/accept；Hermes 要调 LLM API，没网络就是死的 |
| 4 | 多线程 | ENOSYS | clone 带 CLONE_THREAD 一律诚实失败；futex 是 `return 0` 的桩（源码标注 L4，多线程前必须实现）；Node.js 离了线程起不来 |
| 5 | 真实信号 | 假成功 | rt_sigaction 是假成功，未如实标注投递路径 |

另外 rootfs 里现在没有 Python 也没有 Node（只有 perl，且 `mlc perl -e 'print 6*7'`
实测能跑通，说明 glibc 这条链是健康的）。第 3 道尤其硬：mlc 至今零 socket，
而 Hermes 的全部价值就在于联网调模型。

**结论：Hermes Agent 现在装不进 mlc，且不是工作量问题——五道闸一道都没开。**
本轮的实际产出是把第一道闸（M2）的位置、代价、以及"它恰好卡在唯一一个非 PIE
文件 Python 上"这件事摸清了。

## 2026-11-06 晚二轮：把 Claude Code 装进 mlc 的可行性，以及顺带查出的两件事

起因是用户要求「把 claude 装到 mlc」。下载官方
`@anthropic-ai/claude-code-linux-arm64` 2.1.317（npm tarball 154MB，里面是
单个 331MB 原生二进制），硬链进 rootfs/sysroot/usr/local/bin/claude 后实测
`mlc claude --version`，并把过程中撞到的问题逐条查到底。

一、第一道闸就卡死，而且卡得比原先登记的更硬。

ELF 头实测：ET_EXEC（非 PIE），e_entry 0x2ebe058，PT_LOAD 0x200000-0x13e00000，
PT_INTERP /lib/ld-linux-aarch64.so.1，DT_NEEDED 六个（librt、libc、ld-linux、
libpthread、libdl、libm），DT_FLAGS 为 BIND_NOW。`mlc claude --version` 报
「无法映射客户机段（非 PIE 镜像请用基址重写引擎）」errno=12，退出码 1，
与 python3.12 同一道闸、同一个 errno。

**关键新事实：宿主根本不能在 4GB 以下做 MAP_FIXED。** 逐档实测 mmap(MAP_FIXED)
于 0x400000、0x200000、0x1000000、0x40000000（1GB）、0x80000000（2GB）、
0xc0000000（3GB）、0x100000000（4GB）全部 ENOMEM，0x180000000（6GB）与
0x200000000（8GB）成功；无 MAP_FIXED 时内核自选 0x1056fc000。所以第三节里
「镜像按固定地址 MAP_FIXED 落位」在 macOS ARM64 上不存在，M2 只能走
「重定位到客户机窗口 + 改写固有地址」，而后者对 331MB 的二进制是另一个量级
的问题：glibc 的 ld.so 对 ET_EXEC 主映射按 l_addr=0 处理，GOT 与
l_map_start/l_map_end 都用链接期地址，要么改写在内存 phdr 把 p_vaddr 改成
相对值骗过它，要么 mlc 自己接管全部重定位。哪条走得通没有实测。

二、Claude Code 的阻塞链是七道闸，比 Hermes 多两道。

导入符号实测（按 GNU_HASH 解析 dynsym：1247 个符号、515 个未定义）：
socket、connect、bind、listen、accept、accept4、sendto、sendmsg、recvfrom、
recvmsg、socketpair、getaddrinfo；pthread_create/join/detach、pthread_mutex_*、
pthread_cond_*、pthread_rwlock_*、pthread_key_*、pthread_self、pthread_kill 等
三十余个；dlopen/dlsym；epoll_create1/epoll_ctl/epoll_wait/epoll_pwait；
eventfd；prctl；process_vm_readv。另外它是 Bun 编译的单文件二进制（内嵌
JavaScriptCore；本地 darwin 版 otool -L 可见 libSystem/libc++/libicucore/
libresolv，二进制里 1702 处 JavaScriptCore/uv_loop_new/pthread_create），
JSC 要写代码再执行，而 macOS 禁匿名 RWX、宿主进程也没有 allow-jit entitlement。
JIT 这条机制未确证（WebKit 在 Linux 上可能直接 mmap RWX，也可能 RW/RX 切换；
前者不可翻译、后者理论上可），标为待实测。

mlc 侧对照：65 个 case 里 socket 家族 0 个、epoll 家族 0 个、eventfd 0 个、
prctl 0 个、poll/ppoll 0 个；clone 带 CLONE_THREAD 一律 ENOSYS；futex 是
return 0 的桩；rt_sigaction 假成功。**结论：装不进，且第一道就卡死。**
顺带确认了 nr=198 就是 socket：`ls -la` 的 uid/gid 查名会让 glibc 的 NSS 去连
nscd，发出 socket(AF_UNIX, SOCK_STREAM|SOCK_CLOEXEC|SOCK_NONBLOCK, 0)，
即 a0=1、a1=0x80801、a2=0，被 default 分支记成「未实现的系统调用 nr=198」。

三、顺带查出一个 100% 复现的新缺陷 F64：readlinkat 是桩，`ls -l` 全线不可用。

`case SYS_readlinkat` 只认 `/proc/self/exe`，其余路径一律返回 ENOENT（源码
注释写的是「其余 /proc 链接不提供」，但代码把普通文件系统的符号链接也一起
挡了）。后果：任何目录只要含符号链接，`ls -l`/`ls -la` 就报
「cannot read symbolic link」并以退出码 1 结束。对照实验（40 轮每次全复现）：

| 目录 | 符号链接数 | 退出码 | 读符号链接失败处数 |
|---|---|---|---|
| /usr/local/bin | 0 | 0 | 0 |
| /etc | 2 | 1 | 2 |
| / | 3 | 1 | 3 |
| /usr/bin | 23 | 1 | 23 |

失败处数与符号链接数严格相等，100% 确定性问题，与 K2 无关。
README 写着「实测通过：ls、ls -la /」，而 verify.sh 三十八项里没有任何一项测
`ls -l`（只测了 `ls /` 与 `ls /不存在的路径`）——与 F60-F63 同一类：门禁跑绿，
产品不可用。修法很小：非 /proc 路径走 guest_to_host_path 后调宿主 readlink，
把结果抄回客户机缓冲区并返回长度。

四、顺带复测 K2：比登记的严重，而且观测仪器对自己要量的缺陷是盲的。

同一时刻同口径实测（每程序 40 轮，直接调 mlc-core）：`perl -e 1` 失败 26/40，
`perl -e 'print 6*7'` 失败 30/40，`sh -c /usr/bin/id` 失败 4/40 加挂起 1/40；
ls、cat、echo、sh -c true、uname 全干净。换用 `mlc` CLI 复测三批各 30 轮，
失败率 33%、30%、27%，批内稳定；全天不同时段测过 5% 到 75%，波动原因未定位。

**stability.sh 看不到这些失败**：它的判据只有退出码 99（崩溃）与 88（挂起），
其余一律放过——而符号查找失败是退出码 127。当初加这条规则是为了不让
`ls /nonexistent` 的正常退出码 2 被记成崩溃，顺带把 K2 的主要表现形式一起
放过了。所以它这次报「合计崩溃 0/480」，而同一时刻 perl 有 65% 在失败。
**要量化 K2 必须单独数退出码 127**，这是观测仪器本身的缺陷，比 K2 更优先修。

五、本轮排除的两个 K2 假设（都有证据，供下一轮少走弯路）。

1. 补丁把符号表当代码改了——不成立。逐字节核对 libc.so.6 与 perl 的可执行段：
   两类指令命中数（libc 2047、perl 524）与运行期拦截数严丝合缝，且**没有一处
   命中落在 .gnu.hash/.dynsym/.dynstr/.gnu.version/.gnu.version_d/
   .gnu.version_r/.rela.dyn/.rela.plt 里**。libc 的动态链接元数据全在可执行段内
   （文件区间 0x2b8-0x27b88），所以这条一直有人怀疑，但实测是干净的。
   注意原先「命中数与运行期拦截数相等」的推论是循环的，不能作为证据；
   本轮用的是「命中点是否落在元数据节内」，才是真判据。
2. 失败与加载地址相关——不成立。40 轮记录窗口与 ld.so 基址，成功与失败在整个
   地址区间上完全交错，地址余数（mod 16KB）也无区分度。

已确认的失败位置：ld.so 走到 dl_main 末尾的符号与版本核对阶段，前 46 个系统
调用与成功运行逐条同号同构；之后成功运行会多做一次 mprotect（ld.so 自己的
RELRO）、prlimit64、munmap 再继续，失败运行直接报 undefined symbol。
失败符号不固定（calloc、crypt_r、_res、_dl_argv 都见过），TP 存根野值顶替 0 次，
statx 返回 EFAULT 在成功运行里同样出现（不是信号）。

## 2026-11-06 深夜二轮：用户要求「继续修复到可以用的 linux 程序运行」，修掉五个缺陷，K2 水位下降但根因仍未定位

上一轮写「Claude Code 装不进，第一道闸就卡死」时，把它讲成了 mlc 整体不行的证据。
本轮把 252 个 PIE 二进制逐个实测（两轮全量采样，退出码 0 分别是 207 与 210），
把两轮都失败的 29 个逐个看真实输出，全部有解释，没有一个是真缺口：不接受
`--version` 的 getopt 类（clear、captoinfo、infocmp、tic、toe、tabs、reset、tset、
tput、dash、sh），需要 /proc 的（ps、top、pidof），需要 root 或 /etc/shadow 的

二、F64（readlinkat 是桩）已修，`ls -l` 全线恢复。

原实现只认 `/proc/self/exe`，其余一律 ENOENT。改成非 /proc 路径走
guest_to_host_path 后调宿主 readlinkat，结果抄回客户机缓冲区（Linux 的
readlinkat 不补 NUL，返回值就是写入字节数，照做）。修后实测：
`ls -l /etc`、`ls -l /`、`ls -l /usr/bin` 退出码全部为 0，cannot read symbolic link
行数为 0（修前分别是 2、3、23 处且退出码 1），符号链接内容也能正确显示
（`rmt -> /usr/sbin/rmt`）。verify.sh 第 [11] 段新增 ls -l 回归。

三、F65（rootfs 没有 /dev/urandom 一类设备）已修，这是本轮新查出的可用性缺口。

`rootfs/sysroot/dev/` 下只有 `null`（0 字节）与 `y`（2 字节），客户机打开
`/dev/urandom` 一律 ENOENT。glibc 的 malloc 播种、getrandom 回退、任何要熵源的
脚本都会走到这里。做法：openat 对这三个路径改用宿主 /dev/null 做后备 fd
（这样 dup/fcntl/fstat/lseek 全都自然可用），真正的数据由 SYS_read 按标记现造
（urandom 走 arc4random_buf，zero 走 memset），fstat 报成字符设备，lseek 恒返回 0，
close 与 dup/dup3/fcntl(F_DUPFD) 正确传递与摘除标记。
实测 `head -c 16 /dev/urandom`、`head -c 32 /dev/zero`、
`dd if=/dev/urandom bs=8 count=1` 全部退出码 0，随机值逐轮不同。
dd 一开始仍失败，卡在 dup3：设备 fd 原本没有宿主 fd，guest_fd_host 直接返回 EBADF。

四、另外两个真缺陷，与 F64 无关，是区域表的两处簿记错误。

1. `region_covers` 要求整个区间落在**单一条目**内，而 `region_add` 只与第一个
   相交条目合并，相邻映射经常是两条独立条目，于是跨边界的合法指针被判成非法，
   系统调用返回 -EFAULT。改成按区间并集逐段覆盖判定。
2. `SYS_munmap` 把**未对齐**的 `[a0, a0+a1)` 直接交给 region_del，它的「删头部」
   分支会写出未对齐条目（实测形如 `[0x10a5c4018,0x10a5c8000)`），之后
   region_add 的相邻合并、win_free_top 的游标回退都建立在对齐假设上。
   改成只摘宿主真正卸除的那一段 `[page_up(s), page_down(e))`，与 munmap 的
   实际行为一致。修后区域表 11 项全部页对齐，未对齐告警 0 次。
3. `guest_str_ok` 有与第 1 条完全相同的缺陷：只在 p 所在的那一个区域里找 NUL，
   字符串跨到相邻区域就被判非法。同样改成按并集逐段找。

五、stability.sh 的观测盲区已修，K2 第一次变成可观测量。

判据新增退出码 127 并单列为「符号失败」，与崩溃（99）、挂起（88）并列不混淆；
观测列表补入 `ls -l /etc`（F64 回归）与 `perl -e print 6*7`（K2 探针，
实测失败率是 coreutils 的十倍以上）。修后同一时刻即可看出 perl 14/30、
ls -l /etc 5/30 的失败，而修前它报 0/480 全绿。

六、K2：水位下降，根因仍未定位，但排除的假设又多了六条。

单轮通过数从 207/210 升到 217。仍远未到可用。

本轮新增排除的假设（都有证据）：

1. **补丁污染符号表**——用比上一轮更严的方式再证一次：直接离线数八个动态链接
   元数据节里有多少个 4 字节词会命中三种魔数（0xD4000001 与 msr/mrs TPIDR_EL0
   区间），libc、ld.so、perl、ls **四个文件全部为 0**。另外把失败轮次里 libc

   **差异合计 0 字节**。数据是干净的，坏的是查表机制而不是表本身。
2. **补丁因 B 射程超限被跳过**——窗口 96MB 加蹦桌池 16MB 的极限距离约 112MB，

3. **客户机 TCB 落在未登记区域**——那会让所有 TLS 访问被 guest_ptr_ok 误判。
   实测 **0 次**。
4. **两个客户机区域重叠**（后一次 MAP_FIXED 静默卸掉前一次映射）——加重叠检测，
   实测 **0 次**。
5. **pread 短读**——每轮都有 5 次，但字节数逐轮完全一致，且是正常行为
   （客户机按 memsz 请求比 filesz 更大的映射，多出的部分本就该是零页）。
6. **TPIDR 野值相关**——30 轮里 4 轮成功运行出现过野值，失败与野值无相关。

七、本轮最重要的发现：K2 是**时序相关**的，这是下一步唯一的抓手。

实测同一份二进制：`MLC_DEBUG=1` 时 perl 40 轮**零失败**，关掉同一批跑 40 轮

也就是说：只要让引擎在每个系统调用上多花约几十微秒，失败率就从三成掉到几个百分点。
单线程系统里没有真正的竞争，所以这不可能是竞态——更像是引擎侧某段操作
与客户机侧某段操作之间存在一个尚未识别的耦合（例如宿主调用对某些全局状态的
副作用、或补丁写入与客户机取指之间的时序窗口）。**下一轮应当沿这条线查：
先用 MLC_SLOW 做二分，确定敏感的是哪一段系统调用，再逐段加打印定位。**

# 2026-11-07 深夜三轮

本轮目标只有一个：继续攻 K2。结论是修掉两个真缺陷、排除五条假设、
把上一轮两个错误结论推翻，但 K2 的根因仍未定位。

## 一、先更正上一轮的两个结论，它们都没有复现

上一轮写「K2 是时序相关的」，依据是 `MLC_DEBUG=1` 时 perl 40 轮零失败、
关掉后 40 轮失败 12 到 15 次。本轮做四臂对照，每臂 60 轮：

| 臂 | 环境 | 符号失败 |
|---|---|---|
| A | 无 | 8/60 |
| B | MLC_DEBUG=1 | 12/60 |
| C | MLC_SLOW=1 | 13/60 |
| D | 两者都开 | 18/60 |

四臂全在 13% 到 30% 之间，**没有任何一臂接近零**。上一轮那组 0/40 是
单批小样本的统计假象——K2 的失败率在全天范围内会从 0% 漂到 70%，
单批 40 轮根本不足以支撑任何结论。这个教训 2026-11-06 已经记过一次
（当时把 0/40 当成「修好了」，复测 100 轮得 63 次失败），本轮又犯了一遍。

「时序相关」这个说法作废，MLC_SLOW 探针随之作废。真正在全天范围波动的是
失败率本身，与打印、与 CPU 延迟都无关。

## 二、缺陷一（已修）：mrs 存根抹掉调用者手里的 x10

`ML_MRS_STUB` 把选中的线程指针放在 x10 里，出口只还原 x0、x1、x9，
**没有还原 x10**。而客户机的 `mrs xN, TPIDR_EL0` 只写 xN，调用者手里的
x10 可能是活的。

实测全 rootfs 五个二进制的 `mrs TPIDR_EL0` 站点分布：

| 二进制 | mrs 处数 | 目标是 x10 的 |
|---|---|---|
| libc.so.6 | 1530 | 3 |
| perl | 524 | 1 |
| libm.so.6 | 240 | 0 |
| ld-linux-aarch64.so.1 | 29 | 0 |
| libcrypt.so.1 | 0 | 0 |

**合计 2323 处里只有 4 处目标是 x10，也就是 2319 处都会把调用者的 x10
抹成 TCB 地址。** TCB 是已映射的合法地址，抹了不会 SIGSEGV，只会让拿 x10
当指针用的客户机代码读到 TCB 的内容当符号表用——症状与 K2 完全吻合
（「undefined symbol」且失败符号每轮都不同）。

修法：载体换成 x9，出口先还原 x10 再 `orr`，最后才还原 x9；目标寄存器
恰为 x9 时，出口那条 `ldr x9` 由补丁代码改成 nop，否则会把刚写进 x9 的
结果盖回去。词数仍是 19，蹦桌槽大小不变。两处补丁点（`patch_svc_in_range`
与 `load_image2` 内联的那份）都改了。

交替 A/B 100 轮：旧版符号失败 22/100，新版 17/100。差 0.9 倍标准差，
**方向对但幅度不显著**。所以这是真缺陷，却不是 K2 的全部根因。

## 三、缺陷二（已修，危害比缺陷一更直接）：崩溃处理器读 pc-8 时自陷并无限重入

`crash_handler` 直接解引用 `pc-8`、`pc-4`、`pc+4`，而 glibc 的
`_dl_map_segments` 会给段间对齐填充发 `mprotect(PROT_NONE)`，
pc 恰好在段首时前两条就在那种页里。一读就二次故障，**同一个信号在处理器里
反复重入，进程 100% CPU 原地打转，永远走不到末尾的 `_exit(99)`。**

实测证据：本机积了两个这样的进程，其中一个
`./src/mlc-core rootfs/sysroot/usr/bin/sh -c /usr/bin/id` 已经跑了
**11.5 小时、烧掉 414 分钟 CPU**。`sample` 抓栈，838 个样本全部落在
`crash_handler+604`，正是那条 `ldp w8, w9, [x24, #-0x8]`。杀进程前
本机负载长期挂在 3.5 以上。

看门狗对这类进程也失效：`watchdog_handler` 同样会死在 `fprintf` 上。

修法：新增 `crash_rd32()`，按区域表先判可读性再读，不可读返回
`0xFFFFFFFF`（AArch64 未分配空间，任何真指令都不可能是它），由调用方换成
「不可读」字样；三处取值（故障指令行与 SIGSYS 分支）全部改走它；
并在处理器入口 `signal(sig, SIG_DFL)` 兜底——万一还有漏网的解引用，
默认动作会让进程立刻终止，而不是无限重入。

## 四、用七件新工具逐条排除的五条假设

新增 `tests/mlc-k2-*.py` 与 `tests/mlc-regdiff.sh`。其中最有用的一件是
`mlc-k2-imgcmp.py`：**按 PT_LOAD 全量比对客户机映像与 ELF 原文**。
引擎自带的 `MLC_DUMP_DIR` 元数据转储从「可执行段起点 + 0x200」开始，
恰好跳过 `.gnu.hash` 所在的头部——也就是说上一轮「元数据逐字节比对
差异 0 字节」那个结论，比的是一段根本没包含哈希表头的区间。

排除的假设，每条都有证据：

1. **客户机内存被改**——失败轮与成功轮逐字节比对 perl、ld.so、libc、
   libm、libcrypt 五个映像，PT_LOAD 全量。libc 两轮各 488314 字节差异、
   65877 个连续段，**偏移与取值两侧完全相同**（全是 svc 补丁，`54d03bd5`
   一类被改成 B）。表是好的。
2. **link_map 链序错乱**——失败轮链序 perl→libm→libc→ld.so→libcrypt，
   成功轮逐项相同。链没坏。
3. **查找范围缺 libc**——扫 `r_scope_elem`，perl 的 scope 五项
   `[perl, libm, libc, ld.so, libcrypt]`，libc 在列，两轮相同。
4. **查表元数据被改**——libc 的 link_map 里 `l_gnu_bitmask`、
   `l_gnu_buckets`、`l_gnu_chain_zero`、`l_nbuckets`、`l_gnu_symbase`
   六项，两轮相对基址偏移全同。
5. **窗口落点相关**——按 1MB 归并 120 轮，未见到任何聚集。

另外定位到失败发生的**准确位置**：perl 自己的重定位阶段。判据是 RELRO
mprotect 的顺序——失败轮只走到 libc、libcrypt、libm 三处就死，
成功轮还有 perl 自己的 64KB 那处和 ld.so 的那处。

## 五、剩下未排除的：随机性来自宿主侧

加两个探针把客户机侧的随机性全部钉死，失败仍在变：

- `MLC_WIN_ADDR` 钉死窗口基址，五个基址各 12 轮：0/12、2/12、3/12、1/12、5/12。
- `MLC_FIXED_RAND` 再钉死 AT_RANDOM、/dev/urandom、getrandom 三处随机源，
  同五个基址各 12 轮：0/12、2/12、4/12、4/12。
- 客户机映射全部落在窗口内：逐条核对 mmap 返回值，无一落在蹦桌池到窗口末之外，
  所以库的地址与宿主 ASLR 无关。

三条合起来，把剩下的可能性压到宿主侧三项：**宿主 PID**（经
`set_tid_address` 与 `getpid` 喂给客户机，实测每轮不同）、**宿主 malloc
地址**、以及**客户机栈与 brk 预留区这两个独立 `mmap(NULL)` 的位置**。
这是下一轮的方向。

# 2026-11-09 深夜四轮：第一次拿到 ld.so 调用链与系统调用序列

## 一、先修正上一轮的一个结论：MLC_WIN_ADDR 这个探针本身不干净

上一轮用它钉死窗口基址，五个基址各 12 轮失败 0/12、2/12、3/12、1/12、5/12，
据此写「布局无关」。本轮复查发现探针本身有缺陷：`MLC_WIN_ADDR` 只钉窗口，
而 brk 预留区与客户机栈是引擎另外两次独立 `mmap(NULL)`，不受它约束。

实测 `MLC_WIN_ADDR=0x10000000000`：窗口落在 0x10001000000（约 1.1TB），
brk 却自选在 0x1050ec000（约 4.3GB），两者相距约两千倍；正常情况下
brk 紧贴在窗口末之后约 4MB。探针把引擎自身的布局假设整个打破了，
所以「布局无关」这个结论要重新审视，不能直接引用。

## 二、失败符号不是「每轮都不同」，而是「每轮都落在同一个 245 项的集合里」

此前反复说「失败符号每次都不一样」，这句话不准确。把多轮失败符号
汇总后按 perl `.gnu.version` 归类，真相是：

| 观测到的失败符号 | perl 的 ndx | 对应版本与库 |
|---|---|---|
| calloc / fflush / memcpy / pthread_mutex_unlock / __stack_chk_fail / fgetc / mkstemp64 / _IO_2_1_stdin_ / __tunable_is_initialized / obstack_alloc_failed_handler | 2 | GLIBC_2.17，libc.so.6 |
| crypt_r | 9 | XCRYPT_2.0，libcrypt.so.1 |

perl 的 UNDEF 符号按 ndx 分布是 `{1:3, 2:245, 3:8, 4:3, 5:1, 6:4, 7:3, 8:1, 9:1, 10:1}`。
**ndx=2 独占 245 个符号**，失败几乎总是落在这 245 个里，所以看起来「每次都不一样」，
其实是同一个版本项在反复失败。这把搜索空间从「任意符号」收窄到「ndx=2 这一项」。

## 三、第一次拿到客户机调用链：失败确认在 _dl_lookup_symbol_x

新增回溯探针：客户机 `write`/`writev` 的缓冲区里出现 `symbol lookup error`
时，从蹦桌保存块读 x29/x30 顺帧指针链打印。之所以放在 writev 里也查：
ld.so 的 `_dl_fatal_printf` 实测走 writev 不走 write，只在 write 里查一次都没抓到。

一次失败轮的完整链条（ld.so 基址 0x10918c000，偏移即相对基址）：

```
+0xc8c8   _dl_fatal_printf+0x78        ← 打印错误信息处
+0xff8    （_dl_signal_error 之前的本地函数）
+0x1074   _dl_signal_error+0x0
+0x117c
+0x975c   推测 _dl_lookup_symbol_x
+0xd308
+0x18380
+0x15730
+0x16b94
+0x1aa54   推测 dl_main
```

路径与 glibc 源码一致：`dl_main → … → _dl_relocate_object → elf_machine_rela
→ _dl_lookup_symbol_x → _dl_signal_exception → _dl_signal_error → _dl_fatal_printf`。
**失败点是 _dl_lookup_symbol_x，没有异常。**

顺带纠正一个害了很久的记错：**GNU hash 用的是 `h = h*33 + c`（DJB2 变体）**，
不是 `h*16+c`。用 `h*16+c` 做 bucket 自洽检验得 0/958，换成 `h*33+c` 得 958/958。
此前一直用错算法，静态复现查找因此全线失败，白走了很久。

## 四、第一次拿到系统调用序列：失败发生在 perl 自身重定位阶段，且库加载阶段就已分叉

新增 `MLC_SC_TRACE=1`，记录客户机系统调用号序列前 600 个。6 失败 + 13 成功的对比：

- 失败轮长度 46 或 47，成功轮长度 176 到 178（失败轮根本没进 perl 主程序）。
- **5 个失败轮在第 44 项完全一致地分叉**：前 4 个 mprotect 之后，
  成功轮继续 `prlimit64`、`munmap`、`rt_sigaction`×67、`write`，
  失败轮直接 `writev`（错误信息）+ `exit_group`。
- 另有 1 个失败轮（sc-17）**在第 12 项就分叉**：成功轮连续两次 munmap，
  失败轮只有一次 munmap 就接 mprotect。
- 计数：失败轮 mmap 13、munmap 5、mprotect 7、rt_sigaction 0；
  成功轮 mmap 15、munmap 5、mprotect 8、rt_sigaction 67。

结论：失败确实在 ld.so 处理 perl 自身重定位的阶段，与上一轮靠 RELRO mprotect
顺序推出的位置一致；但 sc-17 说明**库加载阶段的映射/解除映射次数已经开始不同**，
分叉比符号查找更早。

## 一、先纠正上一轮的两个结论，它们都不成立

上一轮结尾写「剩下的抓手是钉窗口之后仍在变的 brk 与客户机栈位置」，本轮照此
做了两组实验，两组都否掉了这个方向：

1. **brk 与栈「跟着窗口走」完全无效。** 把 brk 固定贴在窗口末加 4MB、栈固定贴
   在 brk 末加 8MB（也就是把三个自由度合成一个），400 轮交替 A/B：
   新 232/400 = 58.0%，旧（各自自选）233/400 = 58.2%，八个 50 轮分段逐段持平。
   **相对布局不重要。**
2. **绝对地址也不重要——但「固定」重要。** 轮询测四个固定基址各 120 轮：
   1TB 5.8%、2TB 5.8%、4TB 4.2%、6TB 1.7%。四个地址都好，说明不是某个魔法地址，
   而是「离宿主自己的映射足够远」。

把两组合起来才是真相：**起作用的是窗口基址本身取不取固定值，而不是它与 brk/栈
的相对关系，也不是它等于哪个数。**

## 二、定量：300 轮交替 A/B，六个分段逐段占优

## 三、机理：引擎的 C 处理器跑在客户机栈上，宿主指针因此落进客户机区域

这一条是猜的成分最大、但能与全部观测对上的一条，记为待验证假设。

`svc` 修补点跳进的蹦桌第一条就是 `sub sp, sp, #0x110`——**它是在客户机自己的
栈上开帧**，把 x0-x30 全存进去，然后 `blr` 进 C 处理器，C 的帧继续往下叠。
于是引擎每一次处理系统调用，都把一整个宿主 C 栈帧写进客户机栈区域里：格式串
指针、`getenv` 结果、`malloc` 区指针，全是 4GB 一带的宿主地址。

新增探针 `MLC_PROBE_UNREG`（扫客户机内存里指向未登记区域的 8 字节值）实测：
在 ld.so 的活帧附近一次就能抓到 126 处、62 个不同值，顺指针读出来的内容分别是
`[mlc][致命] %s (errno=%d %s)`（引擎自己的 .rodata）、AArch64 指令（引擎自己的
.text）、`ZTUM`（宿主 malloc 区）。**宿主指针确实在客户机内存里。**

而客户机栈是登记过的客户机区域，`guest_ptr_ok` 对落在里面的值一律放行。所以
只要某个宿主指针的数值落进某个客户机区域的地址范围，引擎就会把宿主内存当成
客户机内存读写。窗口自选时落在约 4.3GB，正是宿主 malloc 堆与 mmap 区的所在，
两者数值上紧邻；窗口固定到 1TB 之后，宿主指针（4GB 一带）不可能落进任何客户机
区域，这条路径自然断了。

**待验证**：目前只有「窗口挪远之后失败率降一个数量级」这一条间接证据，还没有
抓到「客户机真的通过宿主指针改写了引擎数据」的现场。要钉死需要给引擎的堆加
金丝雀，或者把 C 处理器换到独立栈上再测一次。

## 四、K2 的失败率不是平稳的，这是本项目第五次在同一处吃亏

5 次（5%）。一次 400 轮 A/B 的内部，前 250 轮两臂都在 12% 到 37%，后 150 轮

## 五、同程序点比对：客户机内存几乎是逐字节相同的

这是本轮最有力的一件排除工具，也是上三轮都没做对的一件。

上一轮的 `MLC_DUMP_AT_SC` 有个缺陷：**退出时的转储会把定点转储覆盖掉**，因为
两个时机写同一批文件名。失败轮死得早、成功轮跑完了 perl，覆盖之后两份文件根本
不是同一个程序点，差分结论全废。已修：`MLC_DUMP_AT_SC` 启用时跳过退出转储，
两者互斥。

修好之后，在第 42 个系统调用处（两侧序列与参数逐项相同，唯一例外是
`set_tid_address` 的返回值即宿主 PID）比对失败轮与成功轮的全量转储：

- 客户机代码与库映像（perl、libc、libm、libcrypt、ld.so）**差异 0 字节**。
- 差异只在三处：TCB 里的 tid（PID）、ld.so 数据段里两个指向 argv/envp 字符串的
  指针、以及客户机栈死区里的引擎栈帧残留。
- 栈哨兵与指针哨兵的值不同，但 `MLC_FIXED_RAND` 只钉了 AT_RANDOM 一处随机源，
  `/dev/urandom` 与 `getrandom` 仍走 `arc4random_buf`，未钉住。

也就是说：**失败不发生在客户机内存状态里。** 这解释了为什么钉客户机布局只能
降一个数量级而不能归零——剩下的变量在宿主侧。

# 2026-11-07 六轮：挂起根因是 wait4 无限等待，已修掉；顺手补齐 4 个 100% 复现的缺实现

本轮从「是否可以正常运行」这个问题出发，结果抓到一个一直没被发现的确定性缺陷。

## 一、挂起的真面目：父进程等一个自己不前进的子进程

`sh -c /usr/bin/id` 偶发挂起（实测 1.3%）。看门狗原来只能给出「PC 落在未知区域」，
本轮给它加了三样东西才有办法定位：`dladdr` 反查宿主库归属、`backtrace` 打宿主调用链、
打印 `getpid()` 区分父子进程。加上之后现场立刻清楚：

- PC 在 `libsystem_kernel.dylib + 0x8204`，符号 `__wait4`；LR 是引擎自己的
  `mlc_syscall_handler_impl`。**是引擎在等子进程，不是客户机死循环。**
- `getpid()` 是父进程，登记的子进程 1 个——等的确实是本引擎 fork 出来的那个。
- PC 与全部通用寄存器在多轮挂起里逐字节相同，说明是一条固定路径。

根因链条三条，缺一条都看不出来：

1. `alarm()` 的定时器**不跨 fork**（POSIX 明确规定）。子进程天生没有看门狗，
   而它恰恰是最容易卡住的那个（execve 之后 longjmp 回 main 重载镜像）。
2. 引擎的 wait4 把客户机的 pid 原样透传宿主 `waitpid`，对「活着但没退出」的
   子进程是无限期睡眠——它不是轮询，是等一个永不到来的 SIGCHLD。
3. 子进程自己不前进，于是父进程、客户机、看门狗一起被拖住。

已修：clone 的子进程分支重新 `watchdog_arm()`；wait4 改成 `WNOHANG` 轮询加
**墙上时钟**上限（`MLC_WAIT4_MS`，默认 2000），超时 SIGKILL 再收割，收割也有
同样上限，仍收不到就返回 ECHILD 并把该 pid 从登记表摘掉。

效果（交替 A/B，每臂 300 轮，看门狗 6s）：`sh -c /usr/bin/id` 挂起 4/300 降到
0/300。代价是最坏情况从「永久挂起」变成「约 4 秒后带错误码退出」（300 轮里 6 轮）。

## 二、轮询按名义睡眠量记账是个假时钟

第一版兜底写成 `waited += 2` 累加 `usleep(2000)` 的名义值。实测机器一忙单次
usleep 实际睡到 10ms，记账 1178ms 时真实已经过去 5.7 秒，看门狗先响——
**兜底形同不存在**。改成 `CLOCK_MONOTONIC` 实测耗时才对。凡是「轮询加超时」的
写法都有这一刀，不能假设睡眠是精确的。

## 三、四个 100% 复现的缺实现，是靠扫 libc 可执行段发现的

先扫客户机 ELF 的 PT_LOAD 可执行段，统计 `mov x8, #imm` 紧跟 `svc #0` 的站点
（脚本 `/tmp/k2r6/svcscan.py`，思路可复用）。`id`/`ls`/`sh`/`perl` 本身 0 个站点
（全动态链接），`libc.so.6` 有 393 个。据此补齐：

1. `nr=158` 是 **getgroups 不是 getpgrp**。我第一版按 getpgrp 实现（返回宿主
   进程组号），`id` 的 groups 输出立刻变成一串垃圾组号——`getgroups(0, NULL)`
   本该只回组数，却拿到一个不小的进程组号，coreutils 按它去读栈上未初始化内存。
   判据是实参形状：`a0=0 a1=0` 正是「先问有多少组」的调用法，而 getpgrp 无参。
   现已按 getgroups 正确实现，`id` 输出真实的 16 个组。
2. `nr=198` 是 `socket(AF_UNIX, SOCK_STREAM|SOCK_CLOEXEC|SOCK_NONBLOCK, 0)`，
   `a1=0x80801` 这个值本身就能确认身份。glibc 的 NSS 在每次取 passwd/group 前
   先探 nscd，`id` 每轮稳定发 4 次，原先全落 default 打「未实现的系统调用」。
   连同 199-212 整族一起处理：socket/socketpair 回 EAFNOSUPPORT，其余回 ENOTSOCK。
   **不能假成功**——假成功会让 glibc 去 connect 一个不存在的
   `/var/run/nscd/socket`，阻塞远比现在严重。
3. `nr=156/157`（getsid/setsid）补上，透传宿主。

## 四、我这一轮自己犯的错，正好是登记表第十四节的活例

「158 是 getpgrp」这个结论我写进了代码注释，还写了一条挺像样的推理
（「glibc 的 getpgrp 是独立内联，不折叠成 getpgid」）。它是错的，而且一跑就错：
`id` 的 groups 输出当场变成垃圾。**表号推断一律要实测确认**，asm-generic 的
150-160 这一段（getpgid 155、getsid 156、setsid 157、getgroups 158、
setgroups 159、uname 160）与 x86-64 完全不同，凭记忆写必错。

## 六、落盘与验证

`src/mlc-core.c`（+254 行）：wait4 三处加固（子进程重新 arm 看门狗、WNOHANG
