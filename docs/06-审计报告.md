# 审计报告

日期：2026-11-06（v1.1 复审更新）
范围：src/mlc-core.c（约 900 行）、tests/mkelf.py、tests/test.s、tests/verify.sh

## 一、代码审计发现（按严重度）

### 中等问题

M1. 客户机指针未校验直接解引用
sys_openat 在 gdirfd != AT_FDCWD 时读 path[0]；若客户机传入野指针，宿主进程直接 SIGSEGV。
本次调试中实测复现过（测试程序传错参数导致 NULL 解引用崩掉整个 mlc-core）。
对策：v1.1 对所有用户指针加基本健全性检查（NULL 与可读性探测），返回 -EFAULT 而不是崩溃。
状态：已修复（v1.1）。实现比原对策更进一步：不是"探测"而是精确的区域表判定，
见 docs/07 第三节。反向自查通过（region_covers 恒真即崩）。

M2. getdents64 的 DIR* 静态表按客户机 fd 索引
static DIR *g_dir[256]：close 时未关闭对应 DIR*，fd 复用后旧 DIR* 泄漏；且并发客户机线程会竞争该表。
对策：close 时联动 closedir；表访问加锁或改线程局部存储。
状态：已修复（v1.1）。close 与 dup3 替换槽位时联动 closedir，表访问加锁；
长时间运行下的泄漏观测列 v1.2（docs/10 T4）。

M3. mmap 的 MAP_FIXED 处理会把长度按宿主页向上取整
返回客户机原地址但实际映射范围更大，客户机后续 munmap 精确长度时可能漏卸一页。
对策：记录每次映射的取整范围，munmap 时按记录卸。
状态：已修复（v1.1）。做法与原对策不同且更强：区域表记录客户机区间，
munmap 卸宿主中间完整页、页内残余 PROT_NONE，不会伤及相邻映射。

### 轻微问题

L1. brk 实现用 MAP_FIXED 紧贴当前 break 映射，未处理映射失败回滚。
状态：已修复（v1.1，增长/收缩失败均保持原 brk 不变并登记/裁剪区域表）。

L2. 蹦床固定放在客户机映射后 0x10000 处，若客户机镜像超过约 128MB，BL 偏移越界（编译期无检查，运行时表现为跳飞）。
状态：已修复（v1.1 加载期强制检查）。原实现是静默截断 BL 立即数导致跳飞，
现改为越界即 die 并给出链接参数提示；越界路径本身未实测（docs/10 记录在案）。

L3. 系统调用表用 switch 手写分发，新增系统调用容易漏默认分支（默认返回 -ENOSYS，行为安全）。
状态：保持（默认分支安全，v1.1 未改结构）。

L4. futex 一律返回 0（假成功），多线程客户机可能死等——M3 实现前保持并在文档声明。
状态：保持待办（M3 阻塞项，源码已标注）。

### v1.1 复审新发现（已修）

F09. dup3 让两个 guest fd 共享同一宿主 fd：旧实现 g_fd_map[a1] = hfd 没有 dup，
关掉其中一个 guest fd 会连带释放另一个的底层描述符；且把 a0==a1 误判为 -EINVAL
（dup3 允许同号 no-op）。已修，缺独立测试载荷（docs/10 T1）。

F10. clock_nanosleep 把 a1（flags）当 remain 指针解引用：睡眠被打断时会往
flags 值指向的地址写 16 字节，写坏调用方内存。已修，缺独立测试载荷（docs/10 T2）。

### v1.1 复审新识别（未修，记录在案）

R7（安全，中）：客户机曾可用 mprotect 改写引擎自身映射（含蹦床）、
或用 mmap MAP_FIXED 覆盖引擎映射。v1.1 已加区间约束封住（docs/07 R7）。

R8（安全，低）：区域表容量 128 写满后 region_add 跳过，后续映射不纳入校验。
当前是安全侧失败（未注册区间访问一律 EFAULT），客户机功能受损但不越权。

T5（测试）：munmap 未对齐地址时"卸前半页不伤后半页"的行为缺专门用例。

## 二、测试资产审计

- verify.sh 原 8 项检查均为可失败断言。但 v1.1 补测时发现第 7 项（getdents64）
  实际依赖 /tmp 既有文件名：缓冲区 2048 字节只列到前约 60 项，
  断言目标换一个排在后面的文件名就失败——一条会假绿的断言，已改为自建子目录（F08）。
  教训：目录列举类断言必须让列举目标完全可控，不能赌环境内容。
- 新增的三项断言（野指针/mprotect/mmap）都经过反向自查：
  把 region_covers 恒真后野指针用例立即 SIGSEGV（退出码 99），确认非宿主 errno 巧合。
- mkelf.py 的重定位应用有计数输出（v1.1 载荷为 36 处），数量不符时说明解析漏项。
- 测试载荷的参数顺序错误（write/openat 三元组）在调试中两次造成误判，均在测试侧修复；引擎侧代码无误。教训：测试程序也要按 ABI 逐参数核对。

## 三、构建与依赖审计

- 核心零第三方依赖：只链接 macOS 系统框架（libSystem/mach）。
- glib/pkgconf/libffi/pcre2 等构建链只服务于已放弃的 QEMU 路线，未进入交付物。
- 交付物 = src/mlc-core.c 单文件 + clang，可复现。

## 四、结论

v1.1 后无阻塞性缺陷。M1/M2/M3 与 L1/L2 已修复并经 11 项验证；
L3/L4 按原判保持待办。dup3 与 clock_nanosleep 的修复缺独立测试载荷，
建议 v1.2 补齐后再进入 M2。


## v1.3 全量审计（2026-11-06）

范围：src/mlc-core.c 全 1742 行通读（上一轮只复审到约 900 行）、src/stub.s、
tests/verify.sh、src/mlc、MLC.command、src/install.sh、打包形态。

### 高危（可被客户机输入直接触发的宿主内存破坏）

A1. 宿主栈缓冲区溢出（已修，F37）
    main() 里 strptr[256] / envptr[160] / words[600] 三个宿主栈数组，
    其中 argv 条数没有任何上界检查。`mlc $(seq 1 500)` 即越界写宿主栈。
    附带一处：客户机栈顶部留白 4096 字节装不下真实环境变量总量，
    字符串写出匿名映射末端，症状是「莫名 SIGSEGV」而不是报错。
    修法：三处硬上限 + 先算词数再落盘 + 留白提到 64KB。
    复现命令：`./src/mlc-core tests/test.elf $(seq 1 300)`
    修复前行为：宿主栈被踩（无稳定复现，属潜在破坏）；
    修复后行为：打印「参数过多（301，上限 128）」并以退出码 2 结束。

### 中危（状态簿记不一致，导致野指针校验失效）

A2. mremap 卸与摘不同区间（已修，F38）
    munmap 用页对齐区间，region_del 用未对齐区间，区域表残留已释放条目，
    guest_ptr_ok 对已卸载地址放行。
A3. MAP_FIXED 失败后区域表说谎（已修，F49）
    先 munmap 再 mmap，mmap 失败时区域表未同步，表里声称可访问而实际已卸载。
    实测崩溃签名正是「故障地址在客户机区域表内=是」。
A4. brk 预留区整体注册成活区间（已修，F50）
    32MB 一次注册，未提交部分被当成合法内存；MAP_FIXED 落在上面时
    触发「先卸后建」，把预留区啃掉一块，后续 brk 增长失败，客户机堆坏掉。
A5. 无 MAP_FIXED 的 hint 被当 MAP_FIXED 用（已修，F39）
    只查引擎保护区、不查活区间相交，一次部分重合的 hint 静默卸掉活数据。
    与 F32 同类损坏，触发点不同。

### 低危（语义错误与陷阱）

A6. sigaltstack(43) 未实现返回 ENOSYS（已修，F46）。曾疑为 K1 根因，实测否证。
A7. set_tid_address 返回常量 4242 当指针（已修，F47）。4242 = 0x1092，
    正是排查 K1 时反复出现的小地址段。
A8. gettid 返回 mach 线程端口号（已修，F45）。
A9. SYS_getpagesz 与 SYS_readlinkat 同号的占位 define（已删，F41）。
A10. SYS_munmap 同一句检查重复两遍（已删，F40）。
A11. MLC.command 的 SHELL_RC 判断两个分支都写 .zshrc，恒真死代码，
     bash 用户会被告知「已写进 .zshrc」然后什么都不生效（已修，按 $SHELL 选 rc）。
A12. stderr 被缓冲，_exit 前诊断全丢，把 K1 的排查带偏两轮（已修，F48）。

### 测试自身的缺陷（本轮一并修掉）

T-a. tests/verify.sh 第 [3] 段用 `MLC_DEBUG=1 ... | grep -q "nr=94"`。
     配 set -o pipefail 时，grep -q 命中即退出会让写入端收到 SIGPIPE，
     整条管道返回 141，断言随机变红。改为先落盘再 grep。
     这是「会让断言完全失效」的典型形态：不是产品错，是仪器错。
T-b. 第 [5] 段原先从 `mlc ls` 的诊断行提区域表用量，但 coreutils 的 ls/cat
     不走 exit_group 那条诊断路径，取不到值。改用 rootfs 里的 sh。
T-c. 验证项从 15 扩到 21（新增 6 项审计回归，全部对准 A1 与 A2 的可观测面）。
