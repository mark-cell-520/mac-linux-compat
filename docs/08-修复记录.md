# 修复记录

日期：2026-11-06
原则：只记真实发生过的修复，每条含现象、根因、修法、验证。

F01. 蹦床写只读页崩溃（SIGBUS，故障地址 = 蹦床内偏移）
现象：svc 修补阶段崩，崩点正是第一处 svc 位置。
根因：mprotect 把文本段改 RX 的循环排在 svc 修补之前，修补写只读页。
修法：调整顺序——先修补 svc，最后才按段 mprotect。
验证：修补数 15 与静态计数一致，后续进入客户机执行。

F02. 存根丢失返回地址（PC 跑到蹦床中间反复执行）
现象：BL 进蹦床后不返回客户机。
根因：blr x9 调用 C 处理器会覆写 LR(x30)，而存根没有保存 LR，最后 ret 回到 blr 之后形成回环。
修法：stub.s 增加 str x30,[sp,#0xA0] 保存、ldr x30 恢复；立即数修补点改为扫描定位（不写死下标）。
验证：客户机连续跨多个系统调用，x19-x23 等寄存器保持正确。

F03. 客户机栈未 16 对齐（SIGBUS，崩在蹦床第二条 stp）
现象：进入蹦床后第一条 stp 即崩，SP 末位是 8。
根因：压栈序列总长度为 8 mod 16，AArch64 PCS 要求 SP 16 字节对齐。
修法：改为字数组整块 memcpy，奇数字数补一个垫字，保证 argc 落在 16 对齐地址。
验证：stp 不再崩，系统调用处理器被正常调用。

F04. mkelf 重定位全部落空（adrp 位移为 0）
现象：测试 ELF 入口指令 adrp 位移 0，数据地址错。
根因：重定位引用的是 .data 的节符号（无名），mkelf 按符号名字解析，落到空符号返回 0。
修法：改为按 r_sym 索引解析符号（节符号取所在节基址 + value）。
验证：22 处重定位应用后入口字节正确（90000020 = adrp +4 页）。

F05. 段页冲突导致文本段变可写（SIGBUS 崩在入口）
现象：mprotect 两段打了同一地址，文本页被数据段的 RW 覆盖，执行即崩。
根因：宿主 16K 页 vs 客户机数据段 4K 对齐（vaddr 0x1000），page_down 把数据段并进文本页。
修法：mkelf 数据段改 16K 对齐；mlc-core 增加段间宿主页重叠检测，保护不同即报错并给出 -Wl,-z,max-page-size=16384 提示。
验证：两段 mprotect 地址分离，客户机入口可执行。

F06. 测试程序参数顺序错误（两次）
现象：write/openat 输出为空或 NULL 解引用。
根因：测试载荷把 write(fd,buf,len) 写成 (buf,len,fd)；openat 漏传 dirfd。
修法：tests/test.s 全部按 Linux ABI x0-x5 逐参数核对重写。
验证：八项验证全过。注：引擎侧无需修改，属测试资产缺陷。

F07. verify.sh 引号配对错误
现象：bash -n 报 unexpected EOF。
根因：$() 内第一个参数少前引号，外层双引号被提前闭合。
修法：OUT=$("$SRC/mlc-core" ...)。
验证：bash -n 通过，8 项检查执行。

F08. getdents64 断言依赖 /tmp 既有内容（测试资产缺陷）
现象：断言 grep "pkg-config|mtest|.log" 能过，改成 grep "mlc-test.txt" 后失败。
根因：getdents64 缓冲区 2048 字节只列到前约 60 项，/tmp 下 mlc-test.txt 排在后面
根本没进输出。原断言能过纯属当时 /tmp 里靠前的文件恰好匹配——一条会假绿的断言。
修法：列举目标改为自建子目录 /tmp/mlc-dent-test，verify.sh 每次 rm -rf 后重建，
里面只放一个 mlc-test.txt，列举结果完全可控。
验证：11 项全过；把子目录改名即断言失败（确认不是恒真）。

F09. dup3 让两个 guest fd 共享同一宿主 fd（引擎缺陷，真实后果）
现象：dup3(old, new) 后 close(new) 会把 old 也一起关掉。
根因：旧实现直接 g_fd_map[a1] = hfd，没有 dup 出新宿主 fd；两个 guest fd
指向同一个宿主 fd，任一 close 都会释放另一个的底层描述符。另外旧实现还把
a0==a1 判为 -EINVAL，而 dup3 允许同号（no-op 返回 new）。
修法：先 dup(hfd) 得到独立宿主 fd，再替换目标槽位；目标槽原有 fd 与目录句柄
联动 close/closedir；a0==a1 直接返回 a1。
验证：编译 + 11 项全过；dup3 路径暂无独立测试载荷，列入 v1.2 测试补齐项。

F10. clock_nanosleep 把 flags 当 remain 指针解引用（引擎缺陷，会写坏调用方内存）
现象：clock_nanosleep(clk, flags, req, rem) 的 a1 是 flags（整数），旧代码
`if (r < 0 && a1 ...) *(struct timespec *)a1 = rem;` 会在睡眠被打断时
往 flags 值指向的地址写 16 字节。
根因：签名记错，nanosleep 与 clock_nanosleep 的 remain 参数位置不同。
修法：按调用号分别取 reqp/remp（nanosleep 取 a0/a1，clock_nanosleep 取 a2/a3），
两者都先过 guest_ptr_ok，再用 memcpy 读写（避免直接解引用未对齐指针）。
验证：11 项全过；clock_nanosleep 路径同样列入 v1.2 测试补齐项。

F11. M1 客户机指针零校验，野指针直接崩宿主进程
现象：客户机 clock_gettime(0, 0xdead0000) 让引擎 SIGSEGV，退出码 99。
根因：handler 对客户机传入指针一律直接解引用，无任何边界检查。
修法：新增客户机内存区域表（加载段/栈/brk 增长区/每次 mmap 区间都登记），
guest_ptr_ok 与 guest_str_ok 两个校验函数，handler 内全部解引用点前置校验，
失败返回 -EFAULT；同时 mprotect/mmap-FIXED/munmap 限制在已注册区间内。
验证：野指针用例返回 -EFAULT 且进程正常退出；反向自查（region_covers 恒真）
立即崩，证明检查真实生效而非宿主 errno 巧合。

F12. M2 目录句柄泄漏：close 不联动 closedir
现象：getdents64 用 fdopendir(dup(hfd)) 建 DIR*，close(gfd) 只 close 宿主 fd，
DIR* 与内部 dup 出的 fd 一直泄漏到进程退出。
修法：DIR* 表提到文件级并加锁；close/dup3 替换槽位时联动 closedir。
验证：11 项全过；泄漏量需长时间运行观察，列入 v1.2 观察项。

F13. M3 munmap 按宿主页取整，会卸掉相邻客户机映射
现象：客户机 munmap(addr, len) 只要 addr/len 未按宿主 16K 对齐，
宿主就把整个页卸掉，同一宿主页内相邻的客户机映射跟着消失。
修法：中间完整页 munmap，页内残余 mprotect PROT_NONE，区域表按客户机区间精确裁剪。
验证：mmap 写入读回 + munmap 用例通过；卸载后再次访问该地址返回 -EFAULT。

以下为 v1.2 动态链接攻坚轮（2026-11-06）：

F14. svc→BL 覆写 LR，glibc leaf 形 syscall 包装死循环（设计级）
现象：ld.so 跑起来后 CPU 100%、不再有系统调用，看门狗抓到 PC==LR==0x1B5CC（__munmap 返回点）。
根因：Linux 的 svc #0 不碰 LR(x30)，而 BL 会把 LR 覆写成「svc 下一条」。
glibc 大量使用 leaf 形 inline syscall 包装（svc; cmn x0,#0xfff; ret），直接靠 LR 返回，
LR 一被覆写，ret 就跳回自己。计数器证实客户机全程只发出 13 次系统调用。
修法：svc 修补成 B（无条件分支，不写 LR）；每个 svc 配一份独立蹦桌副本，
副本末尾用可运行时修补的 B 立即数编码「该 svc 的下一条」，由它把控制权还给客户机。
验证：静态 11 项全过；ld.so 从「卡在 munmap 返回点」前进到能完整加载并报后续库的错误。

F15. brk 区与镜像映射重叠，客户机 brk 增长覆盖蹦桌
现象：直跑 ld.so 时系统调用跳飞。
根因：brk 起点取「主镜像末段之后」，但镜像映射实际跨度是 span+0x14000（含 0x10000 间隔与蹦桌），
brk 起点落在 span 内部，客户机 brk 增长用 MAP_FIXED 覆盖蹦桌。
修法：brk 改独立 32MB 预留区，与任何镜像/蹦桌/其他映射都不重叠，增长超出预留区即失败。
验证：静态 11 项；ld.so 不再因蹦桌被覆盖而跳飞。

F16. mmap 取整相减下溢，所有匿名映射必失败
现象：ld.so 早期 mmap(0, len) 全部返回 -ENOMEM。
根因：addr==0 时 map_addr 取 0x100000000，map_end 取 page_up(len)，两者相减下溢成天文数字。
修法：addr==0 时 map_addr=0、map_end=page_up(len)。
验证：ld.so 的 mmap 全部成功并返回合理地址。

F17. 可执行文件映射匿名化时误剥 MAP_FIXED
现象：libc 文本段被映射到 0x102E20000，引擎却把客户机请求的 0x102E10000 当成功返回。
根因：为绕开 macOS 代码签名限制改为匿名映射时，把 MAP_FIXED 也一起去掉，macOS 于是自行选地址。
修法：保留 MAP_FIXED；只有原本不是 FIXED 时才让内核选地址。
验证：libc 文本段映射到请求地址，ld.so 报错从「failed to map segment」前进到下一步。

F18. macOS 拒绝任意文件的可执行映射，且 offset+len 超文件尾直接 ENOMEM
现象：mmap(fd, PROT_EXEC) 返回 EPERM；文件尾不齐的映射返回 ENOMEM。
修法：所有文件映射统一走「匿名映射 + pread 读入内容」，再 mprotect 到目标权限。
代价：MAP_SHARED 文件映射不再写回文件（ld.so 用 MAP_PRIVATE，可接受，已在源码标注）。
验证：libc 各段映射成功。

F19. macOS 对 MAP_FIXED 部分重叠现有映射返回 ENOMEM
修法：MAP_FIXED 前先 munmap 腾空目标范围，等价于 Linux 内核 elf_map 的原子替换语义。
验证：libc data 段与 text 段共享宿主 16K 页时可正常替换。

F20. v1.1 的 MAP_FIXED 安全约束挡住动态链接
现象：ld.so 报 "libselinux.so.1: failed to map segment"、"libc.so.6: cannot map zero-fill pages"。
根因：v1.1 要求 MAP_FIXED 目标必须已注册（region_covers），而 ld.so 的 zero-fill 洞与
新库段都要映射到尚未注册的新地址。
修法：改为「只禁止覆盖引擎保护区（镜像映射 + 蹦桌），其余地址允许」。
这是 R7/D8 决策点的实际取舍：安全约束从「白名单」收紧为「黑名单」，
既放开 ld.so 又保住翻译层不可被改写。

F21. 动态库的 svc 未被拦截
现象：libc 由 ld.so 映射，不经 load_image，里面的 svc #0 保持原样。
修法：sys_mmap 对可执行映射现场扫 0xD4000001、建邻接蹦桌（128KB，1024 槽，
libc 实测 517 处）、运行时修补 B 与返回立即数。
遗留：蹦桌紧邻 body 会与 ld.so 的地址管理冲突（见 F22）。

F22. 动态蹦桌被 ld.so 覆盖/卸载
现象：SIGBUS，PC 正是蹦桌地址；诊断显示 ld.so 的 MAP_FIXED 目标与蹦桌保护区重叠。
根因：蹦桌紧邻客户机映射，而 ld.so 会复用它认为空闲的地址。
修法：蹦桌纳入引擎保护区，munmap 也过保护区检查（当前为「拒绝」，
ld.so 因此失败，属未完成状态；彻底解法见 docs/04 的 B1 客户机地址窗口架构）。

F23. 静态测试资产未跟随 rootfs 语义
现象：v1.2 加路径重写后，客户机视角的 /tmp 变成 rootfs/tmp，测试仍写真实 /tmp 导致两项失败。
修法：verify.sh 把测试文件写进 rootfs/sysroot/tmp/mlc-dent-test。
教训：客户机根文件系统一旦改变，测试资产的目标路径必须同步，否则会误判成引擎回归。

以下为 v1.2 收尾轮（2026-11-06 续，B6 突破）：

F31. munmap 的页内残余 PROT_NONE 打死相邻映射
现象：客户机 munmap 一段 4K 边界区间后，同一宿主页内的相邻映射不可访问。
根因：宿主按 16K 页取整，`mprotect(hs, s - hs, PROT_NONE)` 的长度被 macOS 向上
取整到整页，把不该碰的相邻数据一起打成不可访问。
修法：只卸 [page_up(s), page_down(e)) 的完整宿主页，首尾残余一律不碰。
代价：客户机视角「已卸载」的子页区间仍可访问，记入已知边界（不伪造精确卸载）。
验证：mmap 写入读回 + munmap 用例仍通过；相邻映射存活由真实 ls 运行反证。

F32. 窗口栈式复用把活映射算成空闲（B6 根因）
现象：SIGBUS，故障指令是 `stur x1, [x2, #390]`，写进 libc 只读文本页；x2 指向
lib A 的 data 段——而那块 data 段已被静默替换。
根因：`win_free_top` 把窗口低水位退到 `page_down(munmap 起点)`。宿主 16K 页 vs
客户机 4K 页，退下去的那一段仍被相邻库占着，下一次 win_alloc 的 MAP_FIXED
就把活数据抹掉。
修法：win_free_top 反复跳过仍然活着的区间，只退到确实已空的边界；
同时把 region_del 调到 win_free_top 之前（顺序反了会永远退不动）。
验证：ls 完整跑通并正确输出；窗口游标不再回退进活映射。

F33. 引擎保护区护住了客户机自己的段
现象：ls 报 cannot apply additional memory protection after relocation: Cannot allocate memory。
根因：guard 表登记的是镜像整个 total，glibc 收尾对自己 RELRO 的 mprotect 被挡。
修法：guard 只从 body_at + span 开始；客户机内容留给客户机自己 mprotect/munmap。
验证：五处 RELRO mprotect 全部成功，ls 正常退出。

F34. macOS libSystem 清掉客户机 TPIDR_EL0
现象：__open_nocancel 崩在 NULL+0x110（errno 写入点）。独立小程序实测：
msr tpidr_el0 写入后只要调用一次 open()，读回就是 0。
根因：macOS 的 libSystem 在自己的调用路径上把 TPIDR_EL0 清零，而 glibc 靠它找 TCB。
修法：蹦桌进 C 处理器前 msr 清零（防止 macOS 把客户机 TCB 当 pthread 用），
返回前写回客户机原值；stub.s 增加 mrs/str/msr + ldr/msr 五条，槽位 128→256 字节。
验证：ls 的 errno 路径恢复正常，glibc 初始化尾段到退出全程无 SIGSEGV。

F35. AT_PAGESZ 报 4096，宿主页是 16384（整类问题的总根因）
现象：ls 把目录列表写到 fd 0 而非 fd 1；libc .data 尾部（含 _IO_2_1_stdout_）
变成零页，stdout 的 _fileno 变 0。
根因：客户机按 4K 对齐算 mapstart/mapsize，引擎按宿主 16K 页落位，
一次 4K 边界的 MAP_FIXED 被展成 16K，把同宿主页内仍被 .data 使用的部分连带卸掉。
修法：auxv AT_PAGESZ 报 16384，让 glibc 的段对齐与宿主页粒度一致。
验证：ls/cat/echo 全部写到正确的 fd；libc .data 内容完整。

F36. gettimeofday 被误实现成 getpgrp（自查抓到的回归）
现象：补 169 号时按 getpgrp 写，客户机每次取时间拿到进程组号——静默数据损坏。
根因：补系统调用时凭编号猜名字，没有从实参形状反向确认。
修法：169 改为 gettimeofday（用 clock_gettime 实现，timezone 固定填 0）。
教训：按编号补实现必须双向确认（实参形状 + 权威表），不能靠印象。


## v1.3 全量审计（2026-11-06）

前提：本轮为「审计—修复—上传」三步走，先通读 src/mlc-core.c 全 1742 行，
再逐条修。以下 F37 起都是本轮新发现并修掉的。

F37. 宿主栈缓冲区溢出（可由客户机参数直接触发）
现象：无（潜在缺陷，审计通读时发现）。
根因：main() 里 strptr[256]、envptr[160]、words[600] 三个数组写在宿主栈上，
      而 argv 条数完全没人管——`mlc $(seq 1 500)` 就让 nstr 越过 256、
      nw 越过 600，直接踩宿主栈。客户机可控输入打到宿主数据结构上。
      另有一处：客户机栈顶部留白只有 4096 字节，真实环境变量总量常有好几 KB，
      字符串会写出匿名映射末端，表现为「莫名 SIGSEGV」而不是报错。
修法：三个数组全部设硬上限（GUEST_ARGC_MAX/GUEST_ENVC_MAX/GUEST_WORDS_MAX 均 128/128/512），
      argc 超限直接报用法错误退出；词数先算后写（写在数组里再检查等于没检查）；
      栈顶留白 4096 提到 65536。
验证：129 个参数被拒并打「参数过多」，100 个参数照常退出 0，
      60000 字节的环境变量跑通。三项都进了 tests/verify.sh 第 [5] 段。

F38. mremap 的区域表区间与 munmap 区间不一致
现象：无（潜在缺陷，审计通读时发现）。
根因：SYS_mremap 里 munmap 用页对齐的 [page_down(a0), page_up(a1))，
      而 region_del 用未对齐的 [a0, a0+a1)。卸掉的比摘掉的多，
      区域表里留下「已释放」的残余条目，guest_ptr_ok 会对已卸载地址返回 true——
      野指针校验被自己松掉。
修法：卸与摘改用同一套页对齐区间。
验证：静态载荷 11 项与动态链接冒烟 4 项无回归。

F39. 无 MAP_FIXED 的 mmap hint 被当 MAP_FIXED 用
现象：无（潜在缺陷，审计通读时发现）。
根因：为了满足 glibc 首段 hint 语义，引擎是拿 MAP_FIXED 去落位的。
      但落位前只查了引擎保护区，没查是否与已注册的客户机区间相交——
      一次与活映射部分重合的 hint 就把那段活数据静默卸掉，
      与 F32（窗口水位算错抹掉 data 段）是同一类损坏，只是触发点不同。
修法：新增 guest_region_overlap()，hint 与活区间相交时退回窗口顺序分配。
验证：动态链接冒烟 4 项通过（ld.so 全程走 hint 路径）。

F40. SYS_munmap 里同一句检查写了两遍
现象：无（冗余代码）。
根因：补注释时把 `if (engine_region_hit(...))` 复制了一份，第二遍除了多打一行
      诊断没有任何作用。
修法：删掉第二遍，注释说明只查一次。
验证：munmap 相关静态载荷通过。

F41. 与 readlinkat 同号的占位常量是个陷阱
现象：无（潜在缺陷）。
根因：`#define SYS_getpagesz 78` 与 `#define SYS_readlinkat 78` 同号。
      aarch64 没有 getpagesz 这个调用，该常量从未被 switch 使用，
      但任何人顺手把它加进 switch 就会把 readlinkat 分支整个吃掉，
      而 ld.so 读 /proc/self/exe 会静默变成 ENOENT。
修法：删掉该 define，原处留注释说明为什么不能有它。
验证：编译通过（未使用常量删除不产生告警）。

F42. 区域表上限过低且用量不可观测
现象：无（健壮性）。
根因：G_REGION_MAX 只有 128。表满之后新映射不再纳入野指针校验，
      而满没满、离满还有多远，运行时完全看不出来。
修法：上限提到 512；exit_group 的诊断行里加「区域表 n/512」，
      把余量变成可观测量。
验证：tests/verify.sh 第 [5] 段实测当前用量 7/512。

F45. gettid 返回 mach 线程端口号
现象：无（语义错误）。
根因：`pthread_mach_thread_np()` 返回的是内核对象名不是 tid，量级还与 getpid 撞值，
      客户机若拿它做线程表索引会串号。
修法：进程内递增分配、每线程一份（__thread + 原子自增）。
验证：编译通过，动态链接冒烟无回归。

F46. sigaltstack(43) 返回 ENOSYS
现象：glibc 早期初始化调它，拿不到成功返回。
根因：未实现，走 default 分支返回 ENOSYS。
修法：按 Linux aarch64 的 stack_t 布局（{void*; int; size_t;} 共 24 字节）自己解，
      不调宿主 sigaltstack——标志位取值两侧不同（Linux SS_DISABLE=2，macOS 是 4）。
      只登记不投递（本引擎不投递信号）。
验证：trace 里不再出现 nr=43；动态链接冒烟无回归。
备注：曾怀疑它是偶发崩溃 K1 的根因，实测补上后崩溃率未变，该猜想不成立。

F47. set_tid_address 返回常量 4242 当指针用
现象：无（潜在缺陷）。
根因：`return 4242;`。glibc 把这个返回值当线程号存下来，
      常量 4242 = 0x1092 正是排查 K1 时反复见到的那个小地址段。
修法：按宿主持性返回真实 pid（单进程单线程时二者同值），
      客户机给的「退出时写线程号」地址原样记住备查。
验证：动态链接冒烟无回归。

F48. stderr 被缓冲，_exit 之前诊断全丢
现象：崩溃时「退出码 99 但没有任何输出」，一度误判成「exit 分支没到达」。
根因：诊断全靠 fprintf(stderr)，而进程走 _exit() 终止——任何缓冲都会在退出时丢掉。
      在 stderr 重定向到文件时尤其明显，把排查带偏了两轮。
修法：main() 开头 setbuf(stderr, NULL)。
验证：崩溃现场（TPIDR、故障地址、寄存器全表）稳定可读。

F49. MAP_FIXED 失败后区域表说谎
现象：偶发崩溃，故障地址「在客户机区域表内=是」但实际已卸载。
根因：两条 MAP_FIXED 路径都是先 munmap 再 mmap（macOS 对部分重叠的 MAP_FIXED
      直接 ENOMEM，必须让路），但 mmap 失败时直接返回错误、区域表没同步改——
      表里仍声称该区间可访问，客户机随后访问已卸载内存，而野指针校验会放行。
修法：munmap 之前先 region_del，失败即意味着簿记已如实；
      同时补 win_free_top 回收窗口水位，并加常驻诊断「MAP_FIXED 覆盖已注册区间」。
验证：崩溃率未变（不是 K1 的根因），但簿记不再说谎，且覆盖行为可观测。

F50. brk 预留区整体被注册成活区间
现象：无（潜在缺陷，实测有 MAP_FIXED 覆盖预留区的痕迹）。
根因：32MB 预留区一次性 region_add 成「活区间」。后果有两个：
      客户机一次 MAP_FIXED 落在未提交部分时被判定为「覆盖活内存」，
      先 munmap 再 mmap 会把预留区啃掉一块，之后 brk 增长的 MAP_FIXED
      落到已卸载页上直接失败，客户机堆就此坏掉；
      未提交部分同时被野指针校验放行。
修法：只登记到当前断点，brk 增长/收缩本身已在 SYS_brk 里同步登记与摘除。
验证：崩溃率未变（不是 K1 的根因），MAP_FIXED 覆盖告警不再对预留区误报。

## v1.4 追加（2026-11-06，第二轮审计）

编号沿用 F51 起。

### F51 蹦桌漏存客户机寄存器（严重，本必修）

缺陷：stub.s v4 只保存 x0-x9、x16-x23、x28、x30，漏掉 x10-x15、x24-x27、x29。
      blr 进 C 处理器会按 AAPCS 把 x10-x15 当调用者保存寄存器踩掉，而我们不还原。
      违反 Linux aarch64 系统调用 ABI——该 ABI 规定除 x0（返回值）外所有寄存器
      原样保留。客户机在 svc 前后放在 x10-x15 里的活值被抹掉。

影响：不是立刻可见的。glibc 的 malloc（sysmalloc/_int_malloc）在 mmap/brk 这类
      svc 两侧用 x10-x15 存临时量，被抹后堆内部状态出错。这也是 K1 排查期
      重点怀疑的一条（后实测否证为根因，但缺陷本身成立）。

修法：stub.s 重写为 v5，帧从 0xB0 扩到 0x110，x0-x30 全部保存还原，x0 最后才
      被返回值覆盖（避免冲掉刚还原的其它寄存器）。ML_STUB 同步换成 48 词，
      保存块布局改为「下标 i 就是 x_i」，TPIDR 在下标 31，返回值槽在下标 32。
      patch_svc_in_range 与 load_image2 的处理器地址修补偏移从 16 改到 21。

回归：tests/regs.elf 把 x10-x15、x24-x27、x29 填哨兵值，发一次 getpid 后逐一
      比对，任一被改动就以该寄存器编号为退出码失败。断言有牙：把 ML_STUB 里
      ldp x10,x11 的还原指令换成 nop，退出码立刻从 0 变 10（实测三次全红）。
      已作为 verify.sh 第 23 项常驻。

### F52 verify.sh 变量名吞全角字符（测试缺陷，错误分支才爆）

缺陷：`bad "mlc ls（退出码 $DRC）"` 与 `bad "mlc cat（退出码 $CRC）"` 里，
      $DRC、$CRC 后面紧跟全角括号。bash 3.2 在多字节 locale 下会把全角字符
      并进变量名，于是只要断言失败要去打失败原因，整个脚本就以
      `unbound variable` 退出——「哪一项红了」反而看不到。

修法：改为 ${DRC}、${CRC}。全文件扫过一遍，无其它同类隐患。

### F53 stability.sh 失败判据错（测试缺陷，读数全错）

缺陷：原脚本把「退出码非 0」一律算失败。于是 `ls /nonexistent` 每次都被记
      失败 200/200——那个程序的正常退出码就是 2（ENOENT），不是崩溃。
      真正的崩溃签名是退出码 99（crash_handler 的 _exit 码）。

修法：判据改为只认退出码 99；观测面从 3 个程序扩到 5 个
      （加 echo hi 与 ls -la /）；抓现场的示例命令同步改成 sh -c true。

### F54 客户机 TPIDR_EL0 写入校验（新增防护，未根除 K1）

背景：见 docs/10 的 K1 节 v1.4 段。macOS libSystem 会把 TPIDR_EL0 当成自己的
      线程槽位用（本机普通 C 进程进程启动就是 0x0/0x1/0x3，本进程是 0x1006 一档），
      并在我们的宿主调用里写进去。客户机一旦 mrs 拿到小值，所有 TP 相对访问
      （errno、栈保护值、cleanup_jmp_buf）都落到近零地址上。

实现：src/tp-stub.s 新增一路存根，与 svc 蹦桌同一套机制（B 跳入、每处一份副本、
      末条 B 立即数运行时修补返回地址）。patch_svc_in_range 与 load_image2 的
      扫描都加上 msr TPIDR_EL0, xN（0xD51BD040|N）；mlc_tp_write_probe 校验写入值，
      >= 0x10000000 记为有效 TCB，否则有有效 TCB 就顶替。系统调用入口再核对一次
      保存块里的值，同理顶替。退出诊断与崩溃现场都打「TP 存根进入次数、
      最后写入值、有效 TCB、野值顶替次数」。

边界：两道闸门都够不着「最后一次系统调用之后到崩溃之前」那段区间，而实测翻野
      正发生在那里（每次系统调用入口核对从未见过野值，客户机自己只写一次且写的
      是有效值）。所以这是防护，不是修复。K1 仍未解决。

### F55 拦住 mrs TPIDR_EL0 读侧，K1 归零（v1.5）

背景：F54 的两道闸门都拦在写入侧，而 v1.5 用新增诊断把翻野区间夹死了：
      每次崩溃现场都是「蹦桌末次还原 0x10xxxxf80（有效 TCB）」对
      「崩溃时 TPIDR_EL0 = 0x1006 一类小值」。即翻野发生在「最后一次系统调用
      之后、崩溃之前」那段只有客户机代码在跑的区间里。

排查（三条全部否证，逐条留档）：
      1. 全 rootfs 816 个 ELF 静态扫 msr TPIDR_EL0，只有 ld.so 两处
         （0x16130 写 x20、0x186b0 写 x26）与 ldconfig.real 一处，libc 与
         所有程序、库一处都没有；ld.so 两处都已修补且运行期只进入一处。
      2. 给 1 到 31 号全部可捕获信号装监听（MLC_SIG_LOG=1），2000 轮里
         收到过信号的运行数为 0——崩溃前没有任何信号到达。
      3. 崩溃现场 PC 前后 64KB 补扫残留 msr，0 处。

修法：既然拦不住写，就拦住读。客户机唯一拿到线程指针的入口是 mrs xN,
      TPIDR_EL0（编码 0xD53BD040|N）。新增 19 词存根 ML_MRS_STUB：
      sub sp 起帧、存 x0/x1/x9/x10、mrs 读现场值、四条 movz/movk 拼出
      &g_guest_tp_good 后 ldr、cbz 判未建立、cmp 判相等、不等则顶替、
      先还原 x0/x1/x9 再 orr 写目标寄存器、起帧还原、末条 B 返回。
      patch_svc_in_range 与 load_image2 的扫描都加上 mrs 站点；nsvc 计数
      同步纳入，否则蹦桌区定容偏小。mrs xzr（N=31）不拦，读了也没用。

顺序为什么这样排：x0/x1 是存根本来就保存的，x9/x10 是工作寄存器，
      x19/x28/x30 它完全不碰。目标寄存器的写入必须放在 x0/x1/x9 还原之后，
      否则还原会把它冲掉；而选中的值要先搬进 x10，因为 x9 马上要被还原。
      七种目标寄存器（x0/x1/x9/x10/x19/x28/x30）tests/tp.elf 逐个覆盖。

回归：tests/tp.elf 端到端钉住整条链——msr 记下有效 TCB、msr 写小值被顶替、
      mrs 读回有效 TCB 且不是小值、七种目标寄存器一致、十个邻存寄存器不被踩、
      跨一次 getpid 之后仍成立、以及「有效 TCB 未建立时 mrs 必须原样返回现场值」。
      去牙实测：关掉 msr 站点识别退出码变 4；把 cbz 目标改回旧下标退出码变 11；
      把 movk 编码少写一位退出码变 99（存根本身 SIGILL）。
      唯一没有牙的是「mrs 站点完全不拦截」——替换只在宿主越界写 TPIDR_EL0 时
      才触发，客户机自己的写入全被 msr 存根接管，从载荷内部观测不到；
      那条路径的证据是 stability.sh 崩溃率归零，不是本断言。已在测试注释里写明。

效果：2000 轮 sh -c true、1500 轮 ls /nonexistent、1500 轮 cat /etc/hostname
      全部 0 次崩溃；同口径 v1.4 基线 43/2000。

性能：单次 mrs 拦截约 0.87 纳秒（约 3 个周期，实测两亿条 mrs 多花 0.17 秒）。
      端到端在噪声范围内：sh -c true 400 次 0.738 秒对 0.798 秒，
      ls / 400 次 0.579 秒对 0.536 秒。

边界：这不是根因修复。macOS libSystem 凭什么在没有宿主调用的间隙里能跑，
      仍无可观测触发点；v1.5 是把不可观测的越界写从客户机的可观测面里屏蔽掉。
      另外单线程模型下「TPIDR_EL0 必须恒等于 g_guest_tp_good」是这条替换的
      前提，多线程（M3）落地后要重做。

### F56 蹦桌池「可写 / 可执行」切换（v1.5）

背景：蹦桌池既要被引擎反复写，又要被客户机当指令跳，而 macOS 禁止匿名映射
      同时可写可执行（实测 mprotect 到 RWX 直接 EACCES）。F55 之前单库拦截数
      只有几百处、一次动态链接跨不了几页，这个矛盾被掩盖着；F55 之后 libc 有
      517 处 svc 加上千处 mrs，跨页数上去后矛盾立刻暴露。

两种错法（都实测崩过，留档免得重复）：
      1. 按 page_up(g_tp_next) 设只读可执行——本次调用安全了，可下一次调用
         分配的地址仍落在已设为只读的页里，写入即 SIGSEGV。
      2. 按 page_down(g_tp_next) 设只读可执行——当前未写满的那一页保持可写，
         于是落在这一页里的蹦桌不可执行，客户机一跳过去就是 SIGBUS
         （实测 ls -la / 崩 199/200，故障指令正是 mrs 存根首条
         sub sp, sp, #0x20，故障页 prot=3 即可写不可执行）。

修法：写之前把已设为只读的整段恢复可写（tp_prepare_write），写完之后再把已用
      整段设为只读可执行（tp_finish_write）。安全性在于 patch_svc_in_range 只从
      系统调用处理器内部被调用，切换发生时客户机代码根本没有在跑（客户机只在
      两次系统调用之间运行），不存在「客户机正踩着某条蹦桌时被改保护」的窗口。

关键细节：tp_finish_write 必须无条件调用。mprotect 补扫那条路（SYS_mprotect）
      常常一个站点都不命中，而 tp_prepare_write 已经把池子恢复成可写了——
      此时若不设回只读可执行就返回客户机，客户机一跳蹦桌就是 SIGBUS。
      实测 ls -la / 崩 199/200，崩溃前最后一次系统调用正是 nr=226。

验证：去牙实测——把 tp_finish_write 改回只在 patched 非零时调用，
      ls -la / 崩 199/200；恢复后 0/200。断言有牙。

### F57 fork/exec 打通（B7，v1.6）

背景：sh -c 里的外部命令一直跑不了。实测 dash 的 posix_spawn 走
      clone(CLONE_VM|CLONE_VFORK|SIGCHLD)（a0=0x4111），我们没实现这条，
      返回 ENOSYS，glibc 的 posix_spawn 直接失败，dash 于是放弃并退出 2。
      带绝对路径时能看到这条调用，PATH 搜索时连调用都到不了。

实现：三个系统调用落到宿主上。
      clone（220）：只认 0x4111（posix_spawn）与 0x0011/0x0000（fork），
      其余一律 ENOSYS。落到 fork()，子进程返回 0 并清零诊断计数。
      CLONE_VM 的「共享地址空间」在 posix_spawn 的用法里无所谓——子进程
      紧接着就 execve 把整个镜像换掉；父进程用 fork 的写时复制本来就更安全，
      不存在「父子互相踩同一块」的窗口。CLONE_VFORK 的「挂起父进程」同理
      可以不做：fork 之后父子地址空间已经独立。
      execve（221）：记下路径与 argv/envp 后 longjmp 回 main 的加载循环，
      重新加载镜像、重建客户机栈、再跳一次入口。必须 longjmp 的理由：
      execve 是从蹦桌 → C 处理器 → impl 的深处被调用的，那里没有路能
      「不返回客户机旧代码」地切到新入口。
      wait4（260）：waitpid，并把状态编码从 BSD 形态翻成 Linux 形态
      （退出码在 bits 8-15、信号在 bits 0-6）。
      main 因此从「一条直路」改成加载循环：setjmp 在循环开头，execve 的
      longjmp 落点就在这里；fd 表只在首次初始化，区域表/guard 表/镜像表/
      brk 区/蹦桌池每次重建，环境变量换成客户机自己给的那份。

踩过的坑（都实测复现过）：
      1. argv/envp 只存客户机指针。longjmp 之后 load_image2 会 MAP_FIXED 落到
         客户机窗口低端，把存着 argv 字符串的旧客户机栈整块盖掉，建新栈时
         读出来的全是空串——exec 出来的 echo 收不到任何参数，
         write 只写出一个换行。改成在 sys_execve 里就抄进宿主缓冲区。
      2. 首次运行也对 guest_path 做了一遍 guest_to_host_path，拼成
         rootfs/rootfs/... 而打不开。execve 的路径才是客户机路径，
         调用方给的 argv[1] 本来就是宿主路径。
      3. SYS_exit 与已有的 exit_group case 重复定义，编译直接报
         duplicate case value。
      4. g_sc_by_nr 是 volatile 数组，memset 会告警，改成显式循环。
      5. AT_EXECFN 原来取 strptr[0]，而字符串是倒序写的，strptr[0] 其实是
         最后一个参数。execve 可能给空 argv，顺手补了占位。

回归：verify.sh 新增第 [8] 段三项（外部命令真的执行了、argv 真的传对了、
      退出码经 wait4 真的透传了）；stability.sh 观测面扩到 8 个程序。
      实测 `sh -c '/usr/bin/echo ZZZZ'`、`/usr/bin/uname -a`、`/usr/bin/id`、
      `/bin/date` 全部正确输出，退出码透传正确（ls 的 ENOENT 是 2）。

边界：多线程仍未实现。带 CLONE_THREAD/CLONE_SETTLS 的 clone 一律 ENOSYS，
      不假报成功。fork 出来的子进程若在不 execve 的情况下继续跑客户机代码，
      地址空间是写时复制的副本，语义上与 Linux 的 fork 一致、与 CLONE_VM 不一致。

### F58 稳定性观测脚本抗挂起（v1.6）

背景：量化 K2 时发现部分客户机有约 0.5% 概率永久挂起，而 macOS 没有 timeout
      命令，一次挂起就能把 tests/stability.sh 永久卡住（实测卡死过两轮）。

修法：改用引擎自带的 MLC_WATCHDOG（默认 20 秒，可用 MLC_WATCHDOG_SECS 覆盖），
      超时的进程以 88 退出，脚本把它单列成「挂起」，既不冒充崩溃（99），
      也不再卡住脚本。观测面同时从 5 个程序扩到 8 个（加三个 fork/exec 形态）。

顺带修掉同一个坑的第二次复发：脚本里 `$CRASH_CODE，挂起判据是 $HANG_CODE`
      的全角逗号被 bash 3.2 吞进变量名，`set -u` 直接 unbound variable 退出。
      已改为 ${CRASH_CODE}、${HANG_CODE}，并全脚本扫了一遍同类模式。
      这个坑在 v1.4 的 T-d 记过一次，爆点都在「刚改过的那几行」。

### F59 newfstatat 的 a2/a3 写反，statbuf 从来没被填（严重，v1.6）

背景：v1.6 打通 fork/exec 后发现 `sh -c '/bin/echo hi'`（绝对路径）能跑，
      而 `sh -c 'ls /'`（PATH 搜索）不行，报 Permission denied、退出码 127。
      追踪看到 dash 的 newfstatat 对 /usr/bin/ls 与 /bin/ls 都返回 0（成功），
      却仍然继续往下找，最后判 EACCES。

定位：用 dash 的 test 内建逐项试——
      `[ -e /usr/bin/ls ]` 通过、`[ -x ]` 通过、`[ -r ]` 通过，
      但 `[ -f /usr/bin/ls ]` 与 `[ -d /usr/bin ]` 恒为假。
      再写一个静态载荷直接调 newfstatat 并把返回值当退出码交出来：242 = -EFAULT。
      两条线索一对照，根因就明确了。

根因：Linux 的 ABI 是
      `newfstatat(int dfd, const char *filename, struct stat *statbuf, int flag)`
      即 a0=dfd、a1=filename、a2=statbuf、a3=flag。实现里把 a2 当 flag、
      a3 当 statbuf，正好写反。于是：
      · flag 判定读的是 statbuf 指针（一个栈地址），AT_SYMLINK_NOFOLLOW 时有时无；
      · statbuf 写入用的是 a3，而 glibc 传下来的 a3 几乎总是 0——
        `if (a3) fill_lstat(...)` 直接跳过，结构体留在调用方的栈上全是零；
      · 返回值始终是 0（成功），客户机看到的是「stat 成功但整个结构体全零」。

为什么一直没被发现：ls/cat/stat 一类 coreutils 在 glibc 2.39 上优先走
      statx（nr=291），而 statx 那条路是对的。只有直接走 newfstatat 的
      消费者才会踩到，dash 的 test 内建正是其中之一。
      连锁后果比想象的严重：dash 的 PATH 搜索靠 S_ISREG 决定要不要用这个文件，
      st_mode 为 0 时所有找到的可执行文件都被判成「非常规文件」而跳过，
      于是 sh -c 里任何靠 PATH 找的外部命令都跑不了。

修法：a2/a3 归位，并把 nofollow 判定改成读 a3、fill_lstat 改成写 a2。
      顺带把 `a0 == -100` 改成 `a0 == (uint64_t)-100`，避免有符号比较的歧义。

回归：verify.sh 新增第 [8b] 段四项——test -f 认得常规文件、test -d 认得目录、
      不存在的路径仍为假（防止把失败也修成成功）、PATH 搜索能定位并执行外部命令。
      去牙实测：把 a2/a3 换回错误写法，前三项里的两项加 PATH 搜索立刻变红
      （29/32）；恢复后 32/32。断言有牙。

## F60 / F61 / F62 / F63（2026-11-06，用户试用时暴露的四个缺陷）

这四个都不是审计或压测找到的，是用户问「我如何打开使用呢」、按 README 的用法
装好之后真的去用，几分钟内撞出来的。前 32 项验证全绿——因为每一项都只在
项目目录里直接调 `src/mlc`，装到别处之后的路、以及"真的写脚本"会用到的路，
一条都没被测过。

### F60 装到 ~/.local/bin 之后的 mlc 完全不能用

现象：`mlc echo hi` 报 `CORE\xNN: unbound variable` 然后退 127。
根因有两层：
1. `src/mlc` 用「脚本所在目录的上一级」当项目根。MLC.command 与 install.sh
   都会把它拷到 `~/.local/bin/mlc`，上一级于是变成 `~/.local`，CORE 算成
   `~/.local/src/mlc-core`——不存在。
2. 报错那句本身还踩着 bash 3.2 的坑：`$CORE，` 里的全角逗号被并进变量名，
   `set -u` 直接让脚本死掉，用户看到的是一句乱码而不是"没找到核心"。
   （同一个坑在本项目已第三次出现，前两次在 stability.sh 与 verify.sh。）
修法：src/mlc 改成三级定位（环境变量 MLC_HOME > 安装时写死的 INSTALL_HOME >
脚本相对位置），两个安装脚本拷过去之后用 sed 把真实项目根写进 INSTALL_HOME
并 grep 校验写成功了。全角逗号改成 `${CORE}`。install.sh 原来只打印
「已装到 ~/.local/bin/mlc」却什么都没做，现在真的装了。
回归：verify.sh 第 [9] 段两项。去牙实测：注掉 INSTALL_HOME 分支 → 退 127 变红。

### F61 clone 漏了 glibc 真正的 fork()，命令替换与管道全部不可用

现象：`mlc sh -c 'echo $(echo hi)'`、反引号、`echo x | cat`、
以及任何带重定向的外部命令，全部报 `Cannot fork`、退出码 2。
根因：客户机创建进程有两条不同的 clone 调用——glibc 的 posix_spawn 用
CLONE_VM|CLONE_VFORK|SIGCHLD（0x4111），而真正的 fork() 用
SIGCHLD|CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID（0x1200011）。
实现只认前两者，于是 fork 这条路整个是 ENOSYS。
为什么没被发现：v1.6 的 fork/exec 三项回归测的是 `sh -c '/usr/bin/echo ...'`，
走的是 posix_spawn；而 posix_spawn 与 fork 是两条路，只测通前者会把后者
整条遮住。dash 的最后一个命令优化让 `sh -c 'ls /'` 不 fork 也能跑，
于是连"外部命令能跑"这个观察都没露馅。
修法：把 0x1200011 也认成 fork，并顺手实现 CLONE_CHILD_SETTID（父进程把子
TID 写进 parent_tidptr）、CLONE_PARENT_SETTID（子进程写 child_tidptr）、
CLONE_CHILD_CLEARTID（退出时清零，glibc 挂在那个地址上的 futex 靠它唤醒）。
带 CLONE_THREAD 等位的仍然一律 ENOSYS，不假报成功。
回归：verify.sh 第 [10] 段前两项。去牙实测：判据改回只认 0x0011 → 立刻变红。

### F62 fcntl(F_DUPFD) 把宿主 fd 号递回客户机，重定向永久泄漏

现象：`sh -c 'echo a; echo b > /dev/null; echo c'` 只打印 a。
根因：F_DUPFD 的宿主返回值是宿主 fd 号，客户机认的是自己的 fd 表。
实现直接把这个号递回去，客户机拿到一个从未登记过的 fd。dash 保存 stdout
正是 `fcntl(1, F_DUPFD, 10)`，还原是 `dup3(10, 1, 0)`——第二次调用时
guest_fd_host(10) 查不到，返回 EBADF，stdout 就永久停在重定向目标上。
MLC_DEBUG 的调用序一看就明白：fcntl 回 10，紧接着 fcntl(10, F_GETFD) 回 -9。
修法：F_DUPFD / F_DUPFD_CLOEXEC 的结果走 guest_fd_alloc 登记成客户机 fd。

### F63 fcntl 命令号两侧不是同一套，锁操作静默做错事

现象：无直接现象，是修 F62 时同一句里看出来的。
根因：Linux F_GETLK=5 / F_SETLK=6 / F_SETLKW=7 / F_DUPFD_CLOEXEC=1030，
宿主是 7 / 8 / 9 / 67。原来不仅不翻译，校验指针时用的还是
`a1 == 1 /*F_GETLK*/ || a1 == 2 /*F_SETLK*/`——那两个数是 F_GETFD/F_SETFD，
于是野指针校验一次都没生效过，而客户机要 F_GETLK 会拿到宿主的 F_GETOWN。
修法：加一张命令号翻译表，指针校验按翻译后的宿主命令号判。
