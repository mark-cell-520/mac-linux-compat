# 调研报告 — macOS 上的 Linux 兼容层

日期：2026-11-06
项目代号：mac-linux-compat（简称 MLC）
目标：不做完整虚拟机，用用户态兼容层（CrossOver / Wine 同构思路）在 macOS 上直接运行 Linux 程序，一键安装。

## 二、关键结论：这个生态位是空的

1. 成熟商业产品 CrossOver 只解决 Windows-on-macOS（底层是 Wine）。
2. macOS-on-Linux 方向有 Darling / kakehashi / macRun；Linux-on-macOS 方向没有对应量级的项目。
3. 现有 macOS 上跑 Linux 的方案全是虚拟机：UTM、Tart、Lima、Colima、Docker Desktop。没有一个走"用户态兼容层"路线。
4. 本题不是重复造轮子，是填补空缺；代价是核心翻译层没有现成参照物可抄，必须自建。

## 二点五、关键转折：QEMU user-mode 在 macOS 上不存在（2026-11-06 实测）

原计划以 QEMU user-mode（qemu-aarch64）为翻译引擎。实测三条路全部封死：

1. qemu 9.0.0 configure 硬禁：host_os 非 linux 时 linux_user 无法启用（--enable-linux-user 直接报错 "linux-user not supported on this architecture"）。
2. qemu 4.2.0 configure 同样限制；且 linux-user/ 与 common-user/ 代码几乎没有 __APPLE__ 分支，说明上游从未支持 macOS 宿主。
3. Homebrew qemu 配方实测：macOS 只构建 softmmu（系统仿真），测试块只验证 qemu-system-*，不含任何 user-mode 二进制。本机无 brew、无预编译包可取。
4. 佐证：GitHub 上唯一"Apple Silicon 跑 Linux ELF"的项目 pwnbox-macos 实际是把 qemu-user 放在 Docker 容器（Linux 内核）里跑，不是原生 macOS。

结论：兼容层引擎必须自研。这正是该生态位空缺的根本原因——现成引擎在 macOS 上不存在。

## 三、技术选型

### 3.1 核心翻译引擎：MLC 自研用户态翻译器（mlc-core）

- Apple Silicon 上 macOS 与 Linux 同为 ARM64 指令集，不需要 CPU 仿真——客户机指令原生执行，这是与"模拟器"的本质区别。
- 拦截方式：加载时把客户机可执行段里的 Linux 系统调用指令 svc #0（0xD4000001）替换为 BL，跳到本进程内的系统调用存根；存根保存寄存器、调用 C 处理器、把 Linux 系统调用翻译成 macOS 宿主调用、返回值写回 x0、恢复寄存器返回客户机。
- 这正是 CrossOver/Wine 的同构思路：用户态翻译，不动内核，不装驱动，不重启。
- 镜像要求：v1 只接位置无关镜像（ET_DYN / static-PIE），加载基址由内核选，客户机启动时自 relocate。非 PIE 的 ET_EXEC 镜像（如 Ubuntu 官方 busybox-static）需要基址重写引擎，列入 M2。

### 3.2 Rootfs：Ubuntu Base 24.04 ARM64 官方 rootfs

- 地址：https://cdimage.ubuntu.com/ubuntu-base/releases/24.04/release/ubuntu-base-24.04.3-base-arm64.tar.gz
- 实测：HTTP 206 可达，29865086 字节（29.8MB），x-gzip。
- 官方最小 rootfs，apt 可直接用，不依赖 Docker 或虚拟机镜像。

### 3.3 运行方式

- v1：mlc CLI 包装（exec / shell / apt），内部调用 qemu-aarch64 + rootfs。
- 无 root 模式：proot（ptrace 路径重映射）作为可选组件；默认用 sudo chroot 之外的第三种方式——直接 qemu -L rootfs 指定 ELF 解释器前缀，多数程序不需要 chroot。
- macOS 没有 binfm t_misc，"双击透明运行"做不到，只能 mlc 前缀或 .app 包装。这是平台硬约束，写入已知限制。

### 3.4 远期方向（M6）

自研 Rust 原生系统调用翻译层（kakehashi 同构），去掉 qemu 依赖：
- 加载 Linux ELF，svc 陷阱拦截，系统调用表映射到 XNU。
- 这是把 MLC 从"包装 qemu"升级为"真兼容层"的关键一跃，工作量以季计，列入远期里程碑，本期不做。

## 四、可行性边界（本期 MVP 能做什么、不能做什么）

能：静态与动态链接的 Linux ARM64 命令行程序、apt 装包、python3/node 等解释型语言、shell 脚本、网络程序（socket 翻译由 qemu 完成）。
不能：GPU/3D、systemd（可用变通方式）、内核模块、ptrace 调试器、硬件直连、内核源码编译（可交叉编译后运行）。

## 五、风险与对策

1. qemu 源码构建耗时（预计 5-15 分钟）：install.sh 全自动，失败有明确报错与回退说明。
2. 部分程序依赖 rootfs 内缺失库：mlc apt 直接装，文档给排查路径。
3. 目录放在图片文件夹（用户指定）：与相册无关的独立子目录，卸载即整目录删除。
