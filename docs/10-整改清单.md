### K1、动态链接路径偶发崩溃（v1.5 已消除）

现象：`mlc ls /nonexistent` 一类「要访问 errno」的路径上，
      v1.4 及以前每次运行有 2% 到 7% 的概率以退出码 99 结束。成功路径
      （`mlc ls /`、`mlc cat /etc/hostname`、`mlc echo hi`）不复现。

v1.5 处置结果：归零。实测 2000 轮 `sh -c true`、1500 轮 `ls /nonexistent`、
1500 轮 `cat /etc/hostname` 全部 0 次崩溃；同口径下 v1.4 基线是 43/2000。

现场签名（崩溃处理已能稳定打出，F48 之后不再丢输出）：
      信号 11，故障地址 = 客户机 TPIDR_EL0 加一个偏移（实测有 -0x648、
      +0x10、+0x20、+0x60、+0x61 等多种），而客户机 TPIDR_EL0 是 0x1006 /
      0x1007 / 0x1008 / 0x100a / 0x100b 一类的野值（正常运行时它是库加载地址，
      形如 0x105bce000）。

复现（v1.5 之后已不复现，留作方法学记录）：
      `for i in $(seq 1 400); do ./src/mlc-core rootfs/sysroot/usr/bin/sh -c true >/dev/null 2>/tmp/f.txt; [ $? -ne 99 ] && break; done`
      然后 `grep -E 'TPIDR|信号 |故障地址|TP 存根' /tmp/f.txt`。
      量化用 `bash tests/stability.sh 200`（判据是退出码 99，见下方 T-d）。

v1.5 拿到的硬证据（都已实测，逐条留档）：

      1. 翻野区间被夹住了。新增诊断把「蹦桌末次还原值 + 当时系统调用号」与
         崩溃现场的 TPIDR_EL0 并列打出，实测每次崩溃都是：蹦桌末次还原
         0x10xxxxf80（有效 TCB），崩溃时 TPIDR_EL0 是 0x1006 一类小值。
         即翻野发生在「最后一次系统调用之后、崩溃之前」那段只有客户机代码
         在跑的区间里，不是蹦桌还原漏了。

      2. 客户机代码不可能写它。全 rootfs 816 个 ELF 静态扫 msr TPIDR_EL0
         （编码 0xD51BD040|N），命中只有 ld.so 两处（0x16130 写 x20、
         0x186b0 写 x26）与 ldconfig.real 一处，libc 与所有程序、库一处都没有。
         ld.so 那两处都已修补，运行期只进入其中一处（TP 存根进入次数恒为 1），
         写入值恒为有效 TCB，野值顶替次数恒为 0。

      3. 也没有信号插进来。给 1 到 31 号全部可捕获信号装了监听（SIGSEGV/
         SIGBUS/SIGILL/SIGSYS/SIGALRM 除外，它们各有用途），实测 2000 轮里
         收到过信号的运行数为 0——崩溃前没有任何信号到达。

      4. macOS 确实会写 TPIDR_EL0。蹦桌按设计在进宿主调用前把它清 0，
         宿主调用后读回来看见 0x0、0x1006、0x1007（约二十分之一的调用会这样）。
         本机普通 C 进程的 TPIDR_EL0 进程启动就是 0x0 / 0x1 / 0x3，
         本进程里是 0x1006 一档——同一类东西，都是 libSystem 的线程槽位遗留。

      结论：写野值的是 macOS libSystem，触发点是它在没有宿主调用的间隙里
      凭什么能跑——这一点没有可观测证据，属于「知其然不知其所以然」。
      v1.5 因此放弃「拦不住写就找不到根因」的思路，改为拦住读：
      客户机唯一拿到线程指针的入口是 mrs xN, TPIDR_EL0，新增 19 词存根核对，
      与已知有效 TCB 不一致就换成有效 TCB。客户机于是永远拿不到野线程指针，
      K1 实测归零。这不是根因修复，是把不可观测的越界写从可观测面里彻底屏蔽。

v1.5 顺带修掉的一处真实缺陷（与 K1 同源，独立成立）：
      蹦桌池既要被引擎反复写、又要被客户机当指令跳，而 macOS 禁止匿名映射
      同时可写可执行。v1.4 按 page_up(g_tp_next) 把已用范围整段设为只读，
      F55 之后拦截数从几百处涨到几千处，这个矛盾立刻暴露：要么后续蹦桌写进
      已只读的页而 SIGSEGV，要么当前未写满的页不可执行而客户机一跳就 SIGBUS。
      现改为「写前恢复可写、写后设为只读可执行」的切换，且收尾无条件执行。
      实测去牙：把收尾改回只在 patched 非零时调用，ls -la / 崩 199/200；
      恢复后 0/200。详见 docs/08 的 F56。

已排除的猜想（都做过实测，均否证，留档免得重复劳动）：
      1. 未拦截的 svc 执行成 macOS 系统调用——libc 的 RX 段 517 处 svc
         与 ld.so 的 48 处全部修补到位，且 libselinux/libpcre2 的 RX 段
         经直接统计确实不含 svc，不存在漏拦。
      2. sigaltstack 返回 ENOSYS 污染 glibc 早期初始化——补上 F46 后崩溃率未变。
      3. set_tid_address 的常量返回值被当成指针——改成真实 pid 后崩溃率未变。
      4. 某个系统调用返回了小地址被客户机当指针——逐个打印返回值，
         只有 fd、read 计数、tid 三类小值，无 mmap/brk 的小返回。
      5. MAP_FIXED 覆盖活区间、brk 预留区被啃——F49/F50 修完簿记不再说谎，
         崩溃率仍未变。
      6. 蹦桌漏存客户机寄存器（v1.4 补）：x10-x15、x24-x27、x29 原先不保存，
         blr 进 C 处理器会踩掉 x10-x15 且不还原，违反 Linux aarch64 系统调用
         ABI。已修为保存还原 x0-x30 全部，并用 tests/regs.elf 钉住。
         这是实打实的缺陷修复，但崩溃率未变，故不是 K1 的根因。
      7. 蹦桌还原漏写 TPIDR_EL0（v1.5 补）：新增「蹦桌末次还原」诊断后实测
         否证——每次崩溃时末次还原值都是有效 TCB。
      8. 信号在两次系统调用之间插入（v1.5 补）：装全量信号监听后实测
         2000 轮 0 次到达，否证。
      9. 客户机执行了漏拦的 msr TPIDR_EL0（v1.5 补）：816 个 ELF 全扫 +
         崩溃现场 PC 前后 64KB 补扫，均无命中，否证。

已知线索：正常运行时客户机 TPIDR_EL0 恰好在 set_tid_address（nr=96）
      这一次系统调用之后变成合法地址；崩溃的那些运行里它始终是野值。
      即「客户机 TLS 指针有没有被正确建立」是分水岭，但建立过程为何
      间歇性失败，v1.5 之后已不影响正确性（读侧被屏蔽），根因仍未定位。

### K2、部分客户机偶发符号查找失败与永久挂起（v1.6 量化发现，未解决）

      另有少数几次永久挂起（客户机代码空转，不再发系统调用，只能靠看门狗杀）。

量化（2026-11-06 v1.6，每程序 150 次）：

      hostname  1/150 退出码 127
      uname、date、env、pwd、arch、nproc、true、echo、ls、cat、sh   各 150/150 干净
      挂起：sh -c /usr/bin/id 30 次里 2 次（`bash tests/stability.sh 30` 可复现）

与本次改动无关的判据：v1.5 已提交版本同口径 478 次里 22 次非零退出、4 次挂起；
      v1.6 当前版本 343 次里 11 次非零、4 次挂起。比例一致，属既有缺陷。
      另外直接跑 `./src/mlc-core rootfs/sysroot/usr/bin/id` 就复现，
      完全不经过 v1.6 新加的 fork/exec 路径。

复现：`bash tests/stability.sh 30`（v1.6 起该脚本带 MLC_WATCHDOG，
      挂起单列，不会再把脚本卡死）；单次挂起现场用
      `MLC_WATCHDOG=8 ./src/mlc-core rootfs/sysroot/usr/bin/id`。

已排除的猜想：
      1. 修补把符号表当代码改了。libc 的 .dynsym/.gnu.hash 与 .text 同在第一个
         R+X 段里，而 patch_svc_in_range 是整段扫描的。已核对：libc.so.6 可执行段内
         svc 517 处 + mrs 1530 处 + msr 0 处 = 2047 处，与运行期打印的
         「动态库可执行映射 0x...，拦截 2047 处」严丝合缝，没有被误补的数据。
      2. 与 K1 同族。出事的运行里 TPIDR 顶替次数并不异常，症状也不是 TP 相对访问
         落到近零地址，而是版本化符号在 libc 里找不到。

未定位的两条线索：
      1. 挂起时最后一条系统调用是 nr=158（arch_prctl 一类），之后客户机代码空转。
         看门狗本该打出卡住时的 PC 与所在镜像，但抓到的两次里那几行没落到 stderr，
         先把看门狗输出链路查通是下一步。
      2. 符号查找失败集中在少数几个程序，且都是「版本化符号找不到」而非「符号不存在」，
         疑似 .gnu.version / .gnu.version_r 一侧出了问题，但还没有直接证据。

### F59 的连带：PATH 搜索为什么长期不可用（v1.6 定位）

`sh -c 'ls /'` 报 Permission denied、退出码 127，这个现象从 v1.2 起就有记录
（当时归到「fork/exec 未实现」B7 名下）。v1.6 打通 fork/exec 后仍然如此，
才查出真正的病根是 F59：newfstatat 的 a2/a3 写反，statbuf 从来没被填。

因果链：newfstatat 不填 statbuf → st_mode 恒为 0 → dash 的 PATH 搜索把
`S_ISREG(st_mode)` 判成假 → 所有找到的可执行文件都被跳过 → dash 报 EACCES。
所以 B7（fork/exec）与这条是两件独立的事，只是症状长得一样。
v1.6 两件都修了，`sh -c 'ls /'` 现在能跑。

教训：glibc 2.39 上的 coreutils 优先走 statx，把 newfstatat 这条路的消费者
全遮住了。要测这条路，得用不走 statx 的消费者——dash 的 test 内建就是。

### 本轮新增的测试自身缺陷（T 系列续号）

T-d. tests/verify.sh 的变量名吞全角字符。`bad "…（退出码 $DRC）"` 里
      $DRC 后面紧跟全角括号，bash 3.2 在多字节 locale 下会把全角字符并进
      变量名，于是只要断言失败、要去打失败原因，整个脚本就以
      `unbound variable` 退出，连「哪一项红了」都看不到。爆点在错误分支，
      所以一直没暴露。已改为 ${DRC}、${CRC}。
T-e. tests/stability.sh 的失败判据。原脚本把「退出码非 0」一律算失败，
      于是 `ls /nonexistent` 每次都记失败 200/200——那个程序的正常退出码
      就是 2（ENOENT），不是崩溃。已改为只认崩溃签名退出码 99，
      观测面也从 3 个程序扩到 5 个。
