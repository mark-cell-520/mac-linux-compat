### K1、动态链接路径偶发崩溃（未解决，v1.4 大幅收窄）

现象：`mlc ls /nonexistent` 一类「要访问 errno」的路径上，
      每次运行有 2% 到 7% 的概率以退出码 99 结束。成功路径
      （`mlc ls /`、`mlc cat /etc/hostname`、`mlc echo hi`）不复现。

现场签名（崩溃处理已能稳定打出，F48 之后不再丢输出）：
      信号 11，故障地址 = 客户机 TPIDR_EL0 加一个偏移（实测有 -0x648、
      +0x10、+0x60、+0x61 等多种），而客户机 TPIDR_EL0 是 0x1006 / 0x1007 /
      0x1008 / 0x100a / 0x100b 一类的野值（正常运行时它是库加载地址，
      形如 0x105bce000）。

复现：`for i in $(seq 1 400); do ./src/mlc-core rootfs/sysroot/usr/bin/sh -c true >/dev/null 2>/tmp/f.txt; [ $? -ne 99 ] && break; done`
      然后 `grep -E 'TPIDR|信号 |故障地址|TP 存根' /tmp/f.txt`。
      量化用 `bash tests/stability.sh 200`（判据是退出码 99，见下方 T-d）。

v1.4 新拿到的硬证据（都已实测，逐条留档）：

      1. 崩溃点的客户机代码已定位到文件偏移。最常见的一处是 libc.so.6
         的 0x284a0，属于 __libc_start_main 尾部：
             mrs  x0, TPIDR_EL0
             sub  x4, x0, #0x600
             ldur q0, [x4, #-0x48]     ← 故障，地址 = TPIDR-0x648
             str  x3, [x0, #0x100]     ← 写 TCB+0x100（cleanup_jmp_buf）
         故障指令 3cdb8080 经汇编器反查确认就是 `ldur q0, [x4, #-0x48]`。
         TPIDR=0x1006 时故障地址恰为 0x9be，与实测逐个吻合。
         另一处是 `ldr x0, [x24, #0x8]`（f9400700），此时 x24 是 0x105f
         一类的野值——同一个病根：客户机拿到的线程指针是小值。

      2. 客户机自己写 TPIDR_EL0 只有一次，而且写的是有效值。全 rootfs 扫过
         msr TPIDR_EL0（编码 0xD51BD040|N，注意 0xD53BD040 是 mrs 不是 msr，
         这点最早认错过，害了一圈）：只有 ld.so 有两处，libc 与所有程序、
         库一处都没有。运行期只进入其中一处（TP 存根进入次数恒为 1），
         写入值恒为有效 TCB（0x10xxxxf80 一档）。野值顶替次数恒为 0。

      3. 每一次系统调用入口核对保存块里的 TPIDR，从未见过野值。也就是说
         翻野发生在「最后一次系统调用之后、崩溃之前」这段只有客户机代码在跑
         的区间里，而那段区间里客户机没有任何 msr TPIDR_EL0 会执行。

      4. macOS 确实会往 TPIDR_EL0 里写自己的小值。蹦桌按设计在进宿主调用前
         把它清 0，宿主调用后读回来看见 0x1006（约二十分之一的调用会这样）。
         本机普通 C 进程的 TPIDR_EL0 进程启动就是 0x0 / 0x1 / 0x3，
         本进程里是 0x1006 一档——同一类东西，都是 libSystem 的线程槽位遗留。

      5. 已加两道闸门，都不能根除：msr TPIDR_EL0 写入点校验（src/tp-stub.s
         + mlc_tp_write_probe，野值换成有效 TCB）、系统调用入口核对保存块
         （野值换成有效 TCB）。因为翻野那段区间两者都够不着。

      结论：写野值的不是客户机代码，而是 macOS libSystem 在两次系统调用之间
      把 TPIDR_EL0 占回去。剩下的问题是「它在没有宿主调用的间隙里凭什么能跑」，
      目前没有可观测的触发点，K1 因此仍未解决。

已排除的猜想（都做过实测，均否证，留档免得重复劳动）：
      1. 未拦截的 svc 执行成 macOS 系统调用——libc 的 RX 段 517 处 svc
         与 ld.so 的 48 处全部修补到位，且 libselinux/libpcre2 的 RX 段
         经直接统计确实不含 svc，不存在漏拦。
      2. sigaltstack 返回 ENOSYS 污染 glibc 早期初始化——补上 F46 后崩溃率未变。
      3. set_tid_address 的常量返回值被当成指针——改成真实 pid 后崩溃率未变。
      4. 某个系统调用返回了小地址被客户机当指针——逐个打印返回值，
         只有 fd、read 计数、tid 三类小值，无 mmap/brk 的小返回。
      5. MAP_FIXED 覆盖活区间、brk 预留区被啃——F49/F50 修完簿记不再说谎，
         崩溃率仍未变。
      6. 蹦桌漏存客户机寄存器（v1.4 补）：x10-x15、x24-x27、x29 原先不保存，
         blr 进 C 处理器会踩掉 x10-x15 且不还原，违反 Linux aarch64 系统调用
         ABI。已修为保存还原 x0-x30 全部，并用 tests/regs.elf 钉住
         （把 ldp x10,x11 的还原换成 nop，退出码立刻从 0 变 10）。
         这是实打实的缺陷修复，但崩溃率未变，故不是 K1 的根因。

已知线索：正常运行时客户机 TPIDR_EL0 恰好在 set_tid_address（nr=96）
      这一次系统调用之后变成合法地址；崩溃的那些运行里它始终是野值。
      即「客户机 TLS 指针有没有被正确建立」是分水岭，但建立过程为何
      间歇性失败尚未定位。

### 本轮新增的测试自身缺陷（T 系列续号）

T-d. tests/verify.sh 的变量名吞全角字符。`bad "…（退出码 $DRC）"` 里
      $DRC 后面紧跟全角括号，bash 3.2 在多字节 locale 下会把全角字符并进
      变量名，于是只要断言失败、要去打失败原因，整个脚本就以
      `unbound variable` 退出，连「哪一项红了」都看不到。爆点在错误分支，
      所以一直没暴露。已改为 ${DRC}、${CRC}。
T-e. tests/stability.sh 的失败判据。原脚本把「退出码非 0」一律算失败，
      于是 `ls /nonexistent` 每次都记失败 200/200——那个程序的正常退出码
      就是 2（ENOENT），不是崩溃。已改为只认崩溃签名退出码 99，
      观测面也从 3 个程序扩到 5 个。
